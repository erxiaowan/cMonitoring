# 测试用例

本文档覆盖三部分：

1. **自动化测试**（178 个，随代码仓库一起提交，`dotnet test` 一键运行）
2. **手工功能测试**（FT-xx，需要真实 Windows 桌面环境）
3. **非功能验证**（NFT-xx / ETW-xx，验证资源占用、不阻塞、精确模式可用性）

---

## 一、如何运行自动化测试

```bash
# 全量运行
dotnet test tests/CWriteWatcher.Tests -c Release

# 只看某一个测试类
dotnet test tests/CWriteWatcher.Tests -c Release --filter "FullyQualifiedName~OffsetCoalescerTests"

# 详细输出（每条用例一行）
dotnet test tests/CWriteWatcher.Tests -c Release --logger "console;verbosity=detailed"
```

> 需要 .NET 8 **SDK**（不是 Runtime）。
> 当前基线：**失败 0 / 通过 178 / 跳过 0**。

测试项目 `CWriteWatcher.Tests` 只引用 `Core` 和 `Etw`，**不引用 `App`**（WinForms 项目在 CI 上无法无头运行）。
因此所有可测逻辑都被刻意下沉到 `Core` / `Etw` 层，UI 层保持"薄壳"。

### 2.2 `ExclusionMatcherTests` — 25 个

**目标**：证明内置排除表既**拦得住**高频系统写入，又**不误伤**用户真实文件。

| 用例 | 断言要点 |
|---|---|
| `内置规则应当排除高频系统路径`（12 组 Theory） | 逐条验证：`pagefile.sys`、`hiberfil.sys`、`swapfile.sys`、`Windows\Temp`、`SoftwareDistribution\Download`、`WinSxS`、`System32\winevt\Logs`、`$Recycle.Bin`、`System Volume Information`、`Defender\Scans`、`Search\Data\Windows.edb`、`Prefetch` 全部被排除 |
| `不应误伤普通用户文件`（4 组 Theory） | `Documents\report.docx`、`Desktop\a.txt`、`Projects\myapp\src\Program.cs`、`ProgramData\MyVendor\config.json` **不得**被排除 |
| `应当按扩展名排除临时文件`（3 组 Theory） | `.crdownload`（浏览器未完成下载）、`Temp\x.tmp`、`.etl`（ETW 自身的日志文件）被排除 |
| `目录前缀匹配应当大小写不敏感` | `c:\windows\temp\A.TXT` 与 `C:\WINDOWS\TEMP\A.TXT` 均命中 |
| `目录规则不应匹配同前缀的兄弟目录` | 规则 `C:\Windows\Temp\` **不得**误伤 `C:\Windows\Temporary\a.txt` |
| `通配规则应当正确匹配` | `C:\MyApp\Logs\*.log` 只匹配 `.log`；`*.bak` 不匹配 `.bak2` |
| `禁用的规则不应生效` | `Enabled = false` 的规则完全不参与匹配 |
| `进程黑名单应当大小写不敏感` | `MsMpEng.exe` / `MSMPENG.EXE` 命中；`chrome.exe`、`null` 不命中 |
| `环境变量应当被展开` | `%LOCALAPPDATA%\MyCache\` 正确展开为真实路径 |

> 其中 `目录规则不应匹配同前缀的兄弟目录` 是一条**回归用例**：
> 早期版本用朴素 `StartsWith` 实现前缀匹配，导致 `C:\Windows\Temp` 规则误伤 `C:\Windows\Temporary`。
> 现由 `PathUtil.IsUnderDirectory` 保证按**路径分隔符边界**判定。

### 2.3 `EventPipelineTests` — 14 个

**目标**：端到端验证 `EventPipeline` 的闸门**顺序**与**抑制原因**是否正确。
测试构造一个真实的有界 Channel + 消费线程，用 `selfProcessId: 999_999` 隔离自身。

闸门顺序（也是实现顺序）：

```
自身 PID → 进程黑名单 → 路径排除 → 模式A新建文件判定 → 阈值判定
        → 治理降级 → 静默时段 → 三层节流 → 触发提醒
```

| 用例 | 断言要点 |
|---|---|
| `自身进程写入应当被排除` | PID 命中自身 → 不提醒，且计入 `ExcludedBySelf` |
| `黑名单进程写入应当被排除` | `MsMpEng.exe` → 不提醒 |
| `排除路径写入应当被丢弃` | `C:\Windows\Temp\big.bin` 100 MB → 不提醒 |
| `低于阈值不应提醒` | 1 MB < 10 MB 阈值 → 不提醒 |
| `达到阈值应当提醒_并带上全部必填字段` | 20 MB → 单条提醒，且**五要素齐全**：时间、路径、大小、进程名（PID+名称）、触发模式；另校验 `SizeIsExact`、`ThresholdScope`、`CollectorMode`、`Notified` |
| `模式A默认只提醒新建文件` | `WriteKind.Modify` 不提醒；`WriteKind.Create` 提醒 |
| `模式A关闭该选项后修改也提醒` | `AnyWriteOnlyNewFiles = false` 后 Modify 也提醒 |
| `同一文件短时间内只提醒一次` | 两条同路径 20 MB → 只 1 条提醒 |
| `静默时段内不弹出提醒` | 静默 00:00–23:59 → 不提醒 |
| `未知路径默认不弹窗` | `Path = null` → 不提醒（只计数） |
| `未知路径开启选项后可以弹窗` | `NotifyUnknownPath = true` → 提醒 |
| `标准模式的估算值应当被标注` | `SizeIsExact = false`，且 `Note` 含「估算」 |
| `管道应当统计各类排除数量` | 4 条事件 → `ExcludedBySelf=1`、`ExcludedByProcess=1`、`ExcludedByPath=1`、`Notified=1` |
| `暂停时不应处理事件` | `Pause()` 后不提醒；`Resume()` 后恢复 |

### 2.4 `ThresholdEvaluatorTests` — 9 个

**目标**：锁定三种阈值口径的语义边界（这是用户最先会质疑的地方）。

| 用例 | 断言要点 |
|---|---|
| `P2_同一文件窗口累计达到阈值应当触发` | 3 MB × 4 = 12 MB，第 4 次触发，`Accumulated = 12 MB` |
| `P2_窗口过期后应当重新计数` | 间隔超过 1 s 窗口 → 计数归零重新开始 |
| `P2_不同文件应当各自独立计数` | 两个 `windowKey` 各 6 MB → 都不触发 |
| `P2_Offset归并后的逻辑写入量应当作为主判据` | 单 IRP 仅 1 MB，但归并后 100 MB → **触发**，`TriggeredByLogicalWrite = true` |
| `P1_单次IRP口径_大文件被拆散时不应触发` | 100 个 1 MB IRP 按 P1 口径**永不触发**（用于反证为什么默认不用 P1） |
| `P3_进程突发口径应当按进程聚合` | 同进程 3 个不同文件各 4 MB → 第 3 次触发 |
| `P3_未启用时应当永不触发` | `ProcessBurstEnabled = false` → 100 次都不触发 |
| `触发后重置窗口_允许同一文件再次触发` | 触发 → `ResetAfterTrigger` → 重新累计可再次触发 |
| `恰好等于阈值应当触发` | 边界值 `size == threshold` → 触发（`>=` 语义） |

### 2.5 `OffsetCoalescerTests` — 7 个

**目标**：验证核心增强点——把 NTFS 拆散的 IRP 碎片还原成一次"逻辑写入"。

| 用例 | 断言要点 |
|---|---|
| `Offset连续的碎片应当被归并为一次逻辑写入` | 10 × 10 MB 连续 Offset → 累计 **100 MB**，`NewLogicalWriteCount = 1` |
| `Offset不连续时应当开启新的逻辑写入` | Offset 从 0 跳到 50 MB → 重新起算，`NewLogicalWriteCount = 2` |
| `超过时间间隔应当开启新的逻辑写入` | Offset 连续但间隔 500 ms > 200 ms → 重新起算 |
| `不同线程应当独立归并_避免交错写打断归并链` | 线程 1/2 交替写同一区域，线程 1 的累计仍正确 |
| `不同FileKey应当独立归并` | 两个 FileKey 互不影响 |
| `Forget应当清除该FileKey的所有线程变体` | `Forget` 后 `TrackedKeys = 0`，且下次同 Offset 重新起算 |
| `超过容量上限时应当清空而不是无界增长` | 写 500 条、`maxEntries = 100` → `TrackedKeys <= 100`（有界性保证） |

> **为什么必须按 `IssuingThreadId` 分组**：多线程并发写同一文件时 Offset 会交错。
> 若全局按 FileKey 归并，线程 2 的写会打断线程 1 的归并链，导致 100 MB 文件被误拆成很多小段。

### 2.6 `PathUtilTests` — 13 个

|---|---|
| `规范化路径`（6 组 Theory） | `\\?\C:\...`、`\??\C:\...`、正斜杠、重复反斜杠、尾反斜杠、`C:` → 全部归一为规范形式 |

### 2.9 `AlertAggregatorTests` — 8 个

| 用例 | 断言要点 |
|---|---|
| `同一进程的多条提醒应当合并为一条` | 3 条 → 1 条，`AggregatedCount = 3`，`Size` 求和，路径文案含「等 3 个文件」且取**最大**那个文件 |
| `窗口未到期时不应冲刷` | 窗口内不冲刷，超时后冲刷 |

### 2.11 `DirectoryWatcherIntegrationTests` — 3 个

**目标**：在**真实文件系统**上验证标准模式采集器（`ReadDirectoryChangesW` + 重叠 I/O）能真正跑起来。
这是唯一一个会创建真实目录、挂真实句柄、等真实内核通知的测试类。

> **测试目录的选择有讲究**：不能用 `Path.GetTempPath()` —— `%LOCALAPPDATA%\Temp\*` 本身就在内置排除表里，
> 采集器在枚举阶段会跳过它，导致测试永远收不到事件。改用用户主目录下的独立子目录。

| 用例 | 断言要点 |
|---|---|
| `连续写入应当持续收到事件_不因NativeOverlapped复用而崩溃` | 挂载句柄后连续写 6 个文件，要求收到 **≥ 6** 个事件；并校验事件路径在 C 盘、`Source = Standard`、`SizeIsExact = false` |
| `停止后应当完全释放_并可反复启动停止` | 连续 3 轮 Start/Stop，每轮 `IsRunning` 正确翻转、`MonitoredDirectories` 归零 |
| `停止后应当能删除被监控目录_说明没有残留独占句柄` | Stop 后 `Directory.Delete` 不抛异常（验证句柄以 `FILE_SHARE_DELETE` 打开且及时释放） |

**为什么必须有这个类**：它抓出了两个纯单元测试完全覆盖不到、但会让程序**彻底不可用**的缺陷，见下一节。

### 2.12 `CWriteWatcher.UiSmoke` — 20 个

**目标**：在**真实 DPI** 下构造真实窗体，检查「肉眼一眼能看出、但编译器和单元测试完全覆盖不到」的界面缺陷。
四个测试类：设置窗体（4 个）、自绘置顶提醒窗（9 个）、日志筛选栏（4 个）、按天统计窗（3 个）。

运行方式：

```bash
dotnet test tests/CWriteWatcher.UiSmoke
```

> **为什么需要 `DpiAwareness.cs`（模块初始化器）**：
> 测试跑在 `testhost.exe` 里，进程的 DPI 感知由**宿主的清单**决定 ——
> 测试程序集自己的 `ApplicationHighDpiMode` 在这里不起作用，
> 结果是 `Control.DeviceDpi` **恒为 96**，在 125% 的真实环境里**测不出任何 DPI 问题**。
> 用 `[ModuleInitializer]` 在任何窗口创建之前调 `SetProcessDpiAwarenessContext(PerMonitorV2)`，
> 把宿主提升为 DPI 感知（实测：awareness 0 → 2，系统 DPI 96 → 120）。

**`SettingsFormLayoutTests`（4 个）**

| 用例 | 断言要点 |
|---|---|
| `所有按钮的高度必须放得下文字` | 每个 `Button` 的 `Height >= PreferredSize.Height`。不满足即说明文字会被纵向裁切 |
| `分组框内的说明标签不得为空` | 每个 `GroupBox` 内的 `AutoSize` 标签必须有非空 `Text`。不满足即说明提示文字占位但不显示 |
| `控件不得超出父容器的可显示范围` | 非 `AutoScroll` 容器内，子控件边界不得超出父容器 `ClientRectangle`。不满足即说明内容被截断 |
| `运行统计必须完整显示且包含丢失事件` | ★ 统计标签是**运行时**拼出来的（行数会变长），而 `GroupBox` 的 AutoSize 是**构造时**算的 —— 断言标签未被纵向裁切、完整落在分组框内，且含「丢失事件」一行 |

**`AlertPopupLayoutTests`（9 个）**

`AlertPopup` 是**完全自绘的顶层窗口**（没有子控件、没有布局引擎兜底），尺寸和文字位置全靠自己算，
所以必须专门测。这里钉死三个真实踩过的坑：

| 用例 | 断言要点 |
|---|---|
| `卡片必须精确贴合内容_外侧只留对称的投影留白` | ★ 卡片外侧四边留白必须相等且 ≤30px。曾因「在 `OnHandleCreated` 里设 `ClientSize`」多出 39 px |
| `所有内容矩形都必须落在卡片内` | 7 个内部矩形（含关闭/文件夹/链接）都不得溢出卡片 |
| `长路径必须只显示文件名` | 深层路径只保留 `f_0000a1.bin`，且完整路径仍保留供 Tooltip 使用 |
| `超长文件名必须被省略号截断且不撑高卡片` | ★ 300+ 字符文件名 → 卡片高度必须与普通文件名**完全一致**，且以 `…` 结尾 |
| `底部链接与关闭按钮必须有可点击区域且在卡片内` | 两个交互元素都有非零命中区域且不越界 |
| `聚合提醒不得提供打开文件夹按钮` | 聚合提醒的 Path 是「… 等 3 个文件」，不是真实路径 |
| `置顶窗必须不抢焦点且不占任务栏` | `ShowInTaskbar=false`、`TopMost=true`、`FormBorderStyle=None`，且 `CreateParams.ExStyle` 含 `WS_EX_NOACTIVATE` 与 `WS_EX_TOOLWINDOW` |
| `文字测量必须把行尾空格计入宽度` | ★ GDI+ 默认**不计行尾空格**，混排会贴在一起。断言 `MeasureWidth("写入  ") > MeasureWidth("写入")` |
| `渲染位图分辨率必须与窗口DPI一致` | 位图分辨率与尺寸、以及与测量 Graphics 的 DPI 三者必须一致（**结构性守卫**，见下注） |

> **已实测有效**：
> - 把布局从 `OnLoad` 改回 `OnHandleCreated` → `卡片必须精确贴合内容…` 红灯；
> - 去掉文件名省略号截断 → `超长文件名必须被省略号截断且不撑高卡片` 红灯
>   （长文件名的自动换行会把卡片撑高，高度不再一致）；
> - 去掉 `StringFormatFlags.MeasureTrailingSpaces` → `文字测量必须把行尾空格计入宽度` 红灯
>   （报 `"写入"=34，"写入  "=34`）。
>
> **关于「位图分辨率」这条，说实话**：它是**结构性守卫**，不是能靠改代码复现红灯的用例 ——
> 在单显示器 + DPI 感知进程下，`new Bitmap(...)` 的默认分辨率本来就等于屏幕 DPI，
> 所以本机把 `SetResolution` 去掉这条**照样通过**（已实测确认）。
> 它真正能拦住的是**多显示器混合缩放**：那时 `new Bitmap` 取系统 DPI（主屏），
> 而 `DeviceDpi` 是窗口所在屏的 DPI，两者不等就会按错误 DPI 栅格化文字。
> 之所以保留，是因为「文字清晰」本身无法用断言表达，只能钉住可量化的前置条件。

**`LogFormFilterLayoutTests`（4 个）**

对应真实反馈：日期筛选显示成半截时间 `2026-10-12 09`，用户要求**只到「天」**。

| 用例 | 断言要点 |
|---|---|
| `时间选择器必须只精确到天` | ★ `CustomFormat == "yyyy-MM-dd"`，且**不含** `HH` / `mm` / `ss`。曾经写成带时分的格式，被宽度裁成半截 |
| `时间选择器宽度必须放得下完整日期文本` | ★ `Width >= 文本宽度 + 控件装饰`。宽度写死会在高 DPI 下裁切 |
| `打开日志窗口时默认查询今天全天` | ★ 默认区间必须是「今天 00:00:00 ~ 今天 23:59:59」。曾经是 `From = To = 现在` → **打开窗口什么都查不到** |

> **已实测有效**（把代码改回原样后）：
> - 带时分的格式 + `Width=150` → `时间选择器必须只精确到天` 与
>   `时间选择器宽度必须放得下完整日期文本` **2 个用例同时红灯**
>   （报「实际 150 px，至少需要 175 px（文本 128 + 控件装饰 47）」）。
> - 去掉整日归一化 + 不显式设默认值 → `打开日志窗口时默认查询今天全天` 红灯
>   （报 `Expected: 00:00:00 / Actual: 09:34:14`）。
> - 把置顶窗布局从 `OnLoad` 改回 `OnHandleCreated` →
>   `卡片必须精确贴合内容_外侧只留对称的投影留白` 红灯（卡片外侧留白被多算）。

**实现要点**：

- 窗体必须在 **STA 线程**上构造，因此每个用例都在专用 STA 线程里跑，再把断言结果带回 xunit 线程。
- 用反射拿 `internal` 的 `SettingsForm` / `AlertPopup` / `LogForm`（`asm.GetType("CWriteWatcher.App.Forms.…")`），
  这样不必给 `App` 加 `InternalsVisibleTo`。
- 无桌面会话（服务 / 无头 CI）时 `Environment.UserInteractive == false`，整体跳过。
- 置顶窗测试会真的 `Show()`，但把窗口移到屏幕外（`Location = (-4000, -4000)`）避免打扰。
  **必须真的 Show** —— 布局在 `OnLoad` 里做，只创建句柄不触发。
- **不等待固定时长，而是等待条件满足**（见下）。

**关于「等待」的一个坑**：

「运行统计」等标签由 1 秒计时器填充。最初的写法是「抽 1.5 秒消息，然后断言」，
单独跑这个项目时 10/10 通过，但用 `dotnet test CWriteWatcher.sln` 让**两个测试项目并发**跑时，
另一个项目会占满 CPU，1.5 秒有时不够 → 偶发失败（实测出现过 1 次）。

**固定时长等待本身就是错的写法。** 现在改为：

```csharp
// 先抽 1.5 秒让计时器有机会首次填充
Pump(1500);

// 再持续抽消息，直到「所有说明标签都有文字」或超时 10 秒
var deadline = Environment.TickCount64 + 10_000;
while (!waitUntil(form) && Environment.TickCount64 < deadline) Pump(100);

// 然后才断言
```

这样正常情况 1.5 秒就结束，被抢 CPU 时最多多等一会儿，而**真正有 bug 时依然会失败**
（已实测：去掉 `Text = text` 后等满 10 秒并报「13 个说明标签没有文字」）。
连跑 6 次整个解决方案，稳定 6/6。

> 这 3 个用例都**验证过「能抓到 bug」**：临时把 `Hint()` 的 `Text = text` 去掉 → 报「13 个说明标签没有文字」；
> 临时把一个按钮改回 `new Button { Width = 90 }` → 报「1 个按钮高度不足」。
> 一个永远通过的测试没有价值。

## 六、回归用例（已修复缺陷）

以下两个缺陷都是**纯单元测试 100% 覆盖不到**、且会让程序**完全不可用**的。记录在此，防止回归。

### 缺陷 1：`NativeOverlapped` 被复用 → 程序启动即崩溃

**现象**：程序启动后几秒内进程静默消失。前台运行才能看到：

```
Unhandled exception. System.InvalidOperationException: NativeOverlapped cannot be reused for multiple operations.
   at System.Threading.ThreadPoolBoundHandleOverlapped.CompletionCallback(UInt32 errorCode, UInt32 numBytes, NativeOverlapped* nativeOverlapped)
   at System.Threading.PortableThreadPool.IOCompletionPoller.Callback.Invoke(Event e)
   at System.Threading.ThreadPoolTypedWorkItemQueue`2...Execute()
   at System.Threading.ThreadPoolWorkQueue.Dispatch()
```

**根因**：`ThreadPoolBoundHandle.AllocateNativeOverlapped` 返回的 `NativeOverlapped*` 是**一次性**的。
在 `ReadDirectoryChangesW` 的完成回调里直接用同一个指针重挂下一轮读请求，就会踩到运行时检查：

```csharp
// ThreadPoolBoundHandleOverlapped.CompletionCallback —— .NET 源码
//
// The Win32 thread pool implementation of ThreadPoolBoundHandle does not permit reuse
// of NativeOverlapped pointers without freeing them and allocating new a new one.
//
if (overlapped._completed)
    throw new InvalidOperationException(SR.InvalidOperation_NativeOverlappedReused);
overlapped._completed = true;
```

而这是在线程池完成回调里抛出的**未处理异常** → 整个进程直接死，连托盘图标都来不及出现。

**修复**：重挂时「先分配新的 → 用新的发起读 → 最后释放旧的」，
并给每个 watcher 加一把锁串行化「完成回调重挂」与「关闭时释放」，避免二者竞态。

**回归用例**：`连续写入应当持续收到事件_不因NativeOverlapped复用而崩溃`

### 缺陷 2：`GetFileAttributesExW` 的 `CharSet` 缺省为 Ansi → 标准模式零事件

**现象**：句柄挂载成功（`MonitoredDirectories > 0`、`HandleCount > 0`），
没有任何错误计数（`ResyncCount = 0`），但**一个事件都收不到**。

**根因**：`DllImport` 的默认 `CharSet` 是 **`CharSet.Ansi`**。声明 `GetFileAttributesExW` 时漏写 `CharSet`，
运行时就会按 ANSI 编组字符串，把 ANSI 字节流喂给**宽字符版本**的 API，
路径被当成 UTF-16 解析成乱码，调用恒返回 `FALSE`。

实测对比（同一台机器、同一路径）：

| 声明方式 | 结果 |
|---|---|
| `[DllImport("kernel32.dll")]`（默认 Ansi） | `返回=False, LastError=2`（ERROR_FILE_NOT_FOUND） |
| `[DllImport("kernel32.dll", CharSet = CharSet.Unicode, ExactSpelling = true)]` | `返回=True, 属性=0x10 (FILE_ATTRIBUTE_DIRECTORY)` |

后果链：`TryGetFileInfo` 恒失败 → `HandleNotification` 对 ADDED / MODIFIED 一律提前 `return` →
`Emit` 永不被调用 → **标准模式完全失效**。
更糟的是这个异常路径被 `ProcessBuffer` 的 `catch` 静默吞掉，连日志都不留痕迹。

**修复**：给 `GetFileAttributesExW` 与 `CreateFileW` 都显式加上
`CharSet = CharSet.Unicode, ExactSpelling = true`（后者原本已写 `CharSet.Unicode`，补 `ExactSpelling` 以确定性解析入口点）。

**回归用例**：同上的集成测试——断言 `count >= 6`，直接卡住这条路径。

### 缺陷 3：`Button.AutoSize` 默认 `false` → 按钮中文被纵向裁切

**现象**：设置界面所有按钮的中文只露出上半截（"打开日志查看器" 底部笔画被切掉）。

**根因**：`Button.AutoSize` 的默认值是 **`false`**，高度被固定为 `ButtonBase` 的默认高度 **23 px**
（一个 96 DPI 时代的常量）。而字体像素高度会随 DPI 缩放：

| DPI | Microsoft YaHei UI 9pt 的 `Font.Height` | 按钮实际需要的高度 |
|---|---|---|
| 100% | 16 px | 23 px（刚好够） |
| **125%（本机）** | **20 px** | **30 px** ← 23 px 装不下，裁掉约 7 px |

**修复**：新增 `Ui.Btn(text, minWidth)` 工厂（`src/CWriteWatcher.App/Forms/Ui.cs`），
统一设 `AutoSize = true` + `AutoSizeMode = GrowOnly` + `MinimumSize.Width`，
让高度随字体自适应、宽度不足时自动加宽。`SettingsForm` 与 `LogForm` 的 21 个按钮全部改走此工厂。

**回归用例**：`所有按钮的高度必须放得下文字`

### 缺陷 4：`Hint()` / `Warn()` 漏了 `Text` 赋值 → 整个界面的提示文字全部不可见

**现象**：设置界面里提示与警告文字的区域是**空白**的——占了布局空间，但什么都不显示。
包括那条很重要的警告：「标准模式下勾选「整个 C 盘」会递归枚举十几万到几十万个目录…」。

**根因**：

```csharp
// ❌ text 参数从未被使用
private static Label Hint(string text) => new()
{
    AutoSize = true,
    MaximumSize = new Size(680, 0),
    ForeColor = Color.FromArgb(0x5F, 0x5E, 0x5A),
};
```

C# **不会对未使用的参数报警**（只对未使用的局部变量/字段报警），所以编译一直是 0 警告。

**修复**：补上 `Text = text`。共 13 个标签受影响。

**回归用例**：`分组框内的说明标签不得为空`

### 缺陷 5：聚合器里 `Size` 全为 0 时丢失文件路径

**现象**：模式 A（任意新写入）下，提醒里文件路径显示为「(未知路径)」，甚至只显示「共 5 个文件」——
但路径其实是知道的。**这是从真实运行日志里发现的**：`events.db` 里出现了 `Path` 为空但 `Notified = 1` 的记录。

**根因**（`AlertAggregator.Add`）：

```csharp
// b.LargestSize 初值是 0
if (record.Size > b.LargestSize)     // 所有事件 Size 都是 0 时，0 > 0 恒为 false
{
    b.LargestSize = record.Size;
    b.LargestPath = record.Path;     // ← 永远不执行，路径丢失
}
```

**触发条件**：一桶（同一进程、5 秒窗口）里**所有**事件的 `Size` 都是 0。
模式 A 下新建一个空文件就会产生 `size = 0` 的 `FILE_ACTION_ADDED` 事件——
实测中卡巴斯基在 `C:\ProgramData\Kaspersky Lab\...\Temp\` 下批量创建空临时文件，正好命中。

**修复**：用 `b.Count == 1` 兜底，保证第一条记录一定写入路径。

```csharp
if (b.Count == 1 || record.Size > b.LargestSize)
{
    b.LargestSize = record.Size;
    b.LargestPath = record.Path;
}
```

**回归用例**（3 个，都在 `AlertAggregatorTests`）：

| 用例 | 断言 |
|---|---|
| `单条零大小事件_提醒仍应带上文件路径` | 单条 size=0 → `Path` 必须等于真实路径 |
| `多条零大小事件聚合_路径不应退化为共N个文件` | 3 条 size=0 → 路径含首条路径，且形如「… 等 3 个文件」 |
| `零大小事件与有大小事件混合_应取最大的那个路径` | 取 size 最大的那条的路径 |

> 已实测：改回 `record.Size > b.LargestSize` 后，前 2 个用例失败（第 3 个本来就通过，
> 因为非零大小最终会设置路径）——说明用例确实卡住了这条路径。

### 缺陷 6：`WNODE_HEADER` 多了一个字段 → 精确模式 `StartTrace` 返回 161

**现象**：切到精确模式后，设置 → 状态显示
「采集器状态：**启动失败：StartTrace 失败，错误码 161**」。161 = `ERROR_BAD_PATHNAME`。

**根因**：`WNODE_HEADER` 里 `TimeStamp` 与 `KernelHandle` 在 Win32 中是**同一个 union 的两种解释**
（共用偏移 16 的那 8 个字节），但被声明成了两个独立字段：

```csharp
public IntPtr KernelHandle;      // 16
public long   TimeStamp;         // 24   ← ❌ 不存在的字段，白占 8 字节
public Guid   Guid;              // 32   （应为 24）
public uint   ClientContext;     // 48   （应为 40）
public uint   Flags;             // 52   （应为 44）
}                                // 合计 56（应为 48）
```

结构体整体胖了 8 字节 → 后续所有字段偏移 8 字节 →
`LoggerNameOffset` 被写到偏移 **124**，而 `StartTrace` 从 **116** 读 → 读到 0
（等于没给会话名）→ 返回 **161 ERROR_BAD_PATHNAME**。

**实测闭环证明**（同一台机器、同样非管理员、同一段代码，只有结构体不同）：

| 结构体 | `WNODE_HEADER` | `EVENT_TRACE_PROPERTIES` | `LoggerNameOffset` | `StartTrace` 返回 |
|---|---|---|---|---|
| ❌ 错误 | 56 | 128 | 124 | **161 ERROR_BAD_PATHNAME** |
| ✅ 正确 | 48 | 120 | 116 | **5 ERROR_ACCESS_DENIED**（非管理员应有的结果） |

**修复**：删掉多余的 `TimeStamp` 字段，让 `WNODE_HEADER` 回到 48 字节。

**为什么以前没发现**：这个缺陷**只在「以管理员身份运行精确模式」时才暴露**。
整个开发过程中从未提权运行过精确模式，所以它一直躺着没被发现——
直到用户在设置里切到精确模式。

**回归用例**（5 个，`EtwStructLayoutTests`，用反射读 `internal` 结构体）：

| 用例 | 断言 |
|---|---|
| `WNODE_HEADER_必须是48字节` | `Marshal.SizeOf == 48` |
| `WNODE_HEADER_各字段偏移必须与Win32一致` | Guid=24、ClientContext=40、Flags=44 |
| `WNODE_HEADER_不得单独声明TimeStamp字段` | 反射查不到 `TimeStamp` 字段 |
| `EVENT_TRACE_PROPERTIES_必须是120字节且关键偏移正确` | size=120、LogFileMode=64、LoggerNameOffset=116 |
| `LoggerNameOffset必须是结构体的最后一个字段` | `offset == size - 4` |

> 这类「P/Invoke 结构体多一个字段」的错误**编译器和普通单元测试都抓不到**，
> 只会在真实调用时返回一个看不懂的错误码。所以必须把尺寸和偏移直接钉死。

### 缺陷 7：`EVENT_TRACE_LOGFILE.LogfileHeader` 被声明成指针 → 提权后访问冲突崩溃

**现象**：修复缺陷 6 之后，切到精确模式（管理员）启动，程序**静默消失**，
托盘图标都没出现。事件日志里留下一条 `APPCRASH`：

```
P1: CWriteWatcher.exe   P7: c0000005   P8: PCH_17_FROM_KERNELBASE+0xC41CA
故障模块名称: StackHash_5622        ← 无法符号化，典型的"调用了一个垃圾函数指针"
```

**根因**：`EVENT_TRACE_LOGFILE` 里 `LogfileHeader` 在 evntrace.h 中是
**`TRACE_LOGFILE_HEADER` 按值内嵌**（280 字节），但被声明成了 `IntPtr`（8 字节）：

```csharp
public EVENT_TRACE CurrentEvent;   // 32  (88 字节，按值 —— 这个是对的)
public IntPtr LogfileHeader;       // 120 ← ❌ 应该是 280 字节的值类型
public IntPtr BufferCallback;      // 128   （原生应为 400）
public IntPtr EventRecordCallback; // 152   （原生应为 424）
}                                  // 合计 176（原生应为 448）
```

于是 `OpenTraceW` 从偏移 **424** 读 `EventRecordCallback`，而结构体只有 176 字节 ——
读到一片垃圾内存当函数指针，`ProcessTrace` 一调用就 **c0000005 访问冲突**。

**修复**：新增 `TRACE_LOGFILE_HEADER`（用 `StructLayout(Size = 280)` 钉死长度，
因为真实定义含 `TIME_ZONE_INFORMATION`(172B) 等嵌套结构，手写字段极易出错），
并把 `LogfileHeader` 改成该值类型。`EVENT_TRACE_LOGFILE` 随之回到 448 字节。

**为什么以前没发现**：这是**缺陷 6 的"下一层"**。缺陷 6 让 `StartTrace` 直接失败，
代码根本走不到 `OpenTrace`；修好缺陷 6 之后才第一次真正执行到这一段。
典型的「修好一个 bug 才暴露出下一个」。

**回归用例**（7 个，追加到 `EtwStructLayoutTests`）：

| 用例 | 断言 |
|---|---|
| `EVENT_DESCRIPTOR与EVENT_HEADER尺寸必须正确` | 16 / 80 |
| `EVENT_RECORD必须112字节且UserData偏移96` | 各关键偏移 |
| `EVENT_TRACE必须88字节_且内嵌EVENT_TRACE_HEADER` | 48 / 88，`Header`@0 |
| `TRACE_LOGFILE_HEADER必须280字节` | 280 |
| `EVENT_TRACE_LOGFILE必须448字节且回调指针偏移424` | 448，`EventRecordCallback`@424 |
| `LogfileHeader必须是值类型而不是指针` | 反射断言字段类型是 `TRACE_LOGFILE_HEADER` |

> 已实测：把 `Size = 280` 改回 8 后，2 个用例立刻失败。

### 缺陷 8：`EVENT_PROPERTY_INFO` 少 3 个 union + 按事件名判定 → 精确模式「261 万事件、零接收」

**现象**：缺陷 6、7 修好后，精确模式显示「运行中 · ETW 实时会话已建立」，但
「接收事件 0 / 事件速率 0 条/秒」——**会话建起来了，一条事件都没进来，而且没有任何报错**。

**定位手段**：程序的「导出 ETW 诊断信息」直接给出了答案：

```
已构建 schema 数量：20    构建失败：0
事件总数：2615687    Write 事件：0        ← 事件其实到了 261 万条！
[ID 12]                                    ← ★ 事件名是空的
    Irp  (InType=16)
      (InType=0)                           ← ★ 字段名每 3 个才有一个
      (InType=1)
    IssuingThreadId  (InType=8)
```

**两个 bug，都在 `TRACE_EVENT_INFO` 解析上：**

**① `EVENT_PROPERTY_INFO` 声明少了 3 个 union（16 → 24 字节）。**
真实定义（tdh.h）：`Flags(4) + NameOffset(4) + {InType,OutType,MapNameOffset}(8) + count(2) + length(2) + Reserved(4) = 24`。
而 `EventSchemaCache` 是用 `Marshal.SizeOf<EVENT_PROPERTY_INFO>()` 当**步长**遍历
`EventPropertyInfoArray` 的 —— 步长偏小 8 字节后，`16×3 = 48 = 24×2`，
**每读 3 个条目才正好落到一个真实条目边界**，于是字段名只出现三分之一、其余全是垃圾
（`InType` 变成 0/1）。这完美解释了「每 3 个才有一个名字」。

**② 用 `schema.Name` 判定事件种类 —— 但 Kernel-File 的 manifest 不提供事件名。**
TDH 返回的 `TRACE_EVENT_INFO.EventNameOffset` **恒为 0**（Microsoft Learn 明确说明
"偏移量为 0 表示该成员未定义"），因此 `schema.Name` 永远是空串，
`switch (name)` 全部落进 `default: return;` —— 261 万事件被静默丢弃。

**修复**：
1. `EVENT_PROPERTY_INFO` 补齐 `Count` / `Length` / `Reserved`，回到 24 字节。
2. `OnEventRecord` **改为按 `eventId` 判定**，不再依赖事件名。
   事件 ID 是用 `wevtutil gp Microsoft-Windows-Kernel-File /ge:true` 导出的
   **关键字掩码**反推确认的（Create=FILEIO|CREATE、Write=FILEIO|WRITE…），
   顺带修正了两个错的常量：**Delete 19→26**、**Rename 20→27/28**。
3. `PayloadWalker` 放宽字段名匹配 —— 实测偏移量字段叫 **`ByteOffset`** 而不是 `Offset`，
   写入大小可能是 `IoSize`。注意**不能**把 `Length` 当写入大小（Rename 的 `Length` 是新文件名长度）。

**回归用例**（2 个，追加到 `EtwStructLayoutTests`）：

| 用例 | 断言 |
|---|---|
| `TRACE_EVENT_INFO_HEADER必须112字节` | 112，`PropertyCount`@100，`PropertyArrayOffset`=112 |
| `EVENT_PROPERTY_INFO必须24字节` | 24，`InType`@8，`Count`@16，`Length`@18，`Reserved`@20 |

> 已实测：去掉那 3 个 union 后该用例立刻失败。

### 缺陷 9：`Create` 事件里没有 `FileKey`，代码却拿它当映射表的键 → 精确模式「40 万次写入、零提醒」

**现象**：缺陷 8 修好后，精确模式的 schema 解析终于正常了（字段名完整、`Write 事件` 不再为 0），
但**依然一条提醒都不弹**。第二份诊断报告：

```
采集模式：Precise        是否管理员：是        治理级别：L0 正常
接收事件：247529
未知路径：247529          ← ★ 100% 是"未知路径"
触发：0    已提醒：0
路径映射命中率：0%

事件总数：16768527    Write 事件：400080
路径映射：命中 0 / 未命中 400080（命中率 0%），当前条目 0    ← ★ 映射表始终是空的
```

**关键线索在诊断报告的字段清单里**（这是缺陷 8 之后新加的 schema 导出功能带来的）：

```
[ID 10]  NameCreate        FileKey, FileName                       ← FileKey 空间唯一的来源
[ID 12]  Create            Irp, FileObject, IssuingThreadId,
                           CreateOptions, CreateAttributes,
                           ShareAccess, FileName                   ← ★ 没有 FileKey！
[ID 16]  Write             ByteOffset, Irp, FileObject, FileKey, …
```

**根因**：`HandleCreate` 的签名是 `HandleCreate(ulong key, ...)`，调用方传的是
`fields.FileKey`。但 **`Create(12)` 事件的 payload 里根本没有 `FileKey` 字段** ——
它只有 `FileObject`。于是 `key == 0`，函数在第一行 `if (key == 0) return;` 直接返回，
**FileKey→路径 映射表永远是空的**，所有写入都解析不出路径 → 全部被当作"未知路径"丢弃。

而真正携带 `FileKey + FileName` 的是 **`NameCreate(10)`** —— 这个事件**代码里完全没处理**。

**第二个相关缺陷**：`CreateNewFile(30)` 的关键字是 `CREATE_NEW_FILE(0x1000)`，
而订阅关键字只有 `FILENAME | FILEIO | CREATE = 0x10 | 0x20 | 0x80`。
**事件 30 根本不会到达**，于是模式 A 的「仅提醒新建文件」把所有写入都判成"修改已有文件"，
**一条提醒都不弹**（且没有任何报错）。

**第三个相关缺陷**：`EVENT_ID_SET_END_OF_FILE` 被定为 `18`，但 18 实际是 `SetDelete`。
而且 21 个已知 schema 里**没有任何一个含 `EndOfFile` 字段**，所以 `fields.EndOfFile` 恒为 0，
`HandleSetEndOfFile` 里的 `if (fields.EndOfFile == 0)` 恒成立 —— 每次 `SetDelete`
都会误删「新建文件」标记。

**修复**：

| # | 修复 |
|---|---|
| 1 | **新增 `KernelFileEventRouter`（纯函数）**，把「事件 ID + 字段 → 动作 + 键」的分发逻辑从 ETW 回调里抽出来，使其**可被单元测试覆盖** |
| 2 | `Create(12)` / `CreateNewFile(30)` 改用 **`FileObject`** 当映射键；`NameCreate(10)` 用 `FileKey` |
| 3 | `Write(16)` 查询时**两个键都试**（`FileObject` 优先，`FileKey` 兜底）—— Write 两个字段都有 |
| 4 | `Cleanup(13)` / `Close(14)` **只移除 `FileObject` 映射**：`FileObject` 是内核对象地址会被快速回收，必须移除；`FileKey` 是文件持久标识，同一文件可能还有别的句柄在用 |
| 5 | 订阅关键字补上 `CREATE_NEW_FILE(0x1000)`、`DELETE_PATH(0x400)`、`RENAME_SETLINK_PATH(0x800)` |
| 6 | 事件 ID 常量按 `wevtutil gp … /f:xml` 的 `<task>` 列表**全面校正**，并新增 `EtwNative.EventIdName()` 让日志与诊断报告能显示事件名 |
| 7 | 删掉基于 `EndOfFile` 的错误判定，改为 `SetInformation(17)` + `InfoClass == FileEndOfFileInformation(20)` |
| 8 | `DirEnum(20)` / `DirNotify(25)` **明确不用于建映射** —— 它们的 `FileName` 是目录名或搜索模式，不是被写入的文件 |

**回归用例**：新增 `KernelFileEventRouterTests`（**42 个**），把分发逻辑彻底钉死：

| 用例 | 断言要点 |
|---|---|
| `事件ID与名称的对应关系必须与系统manifest一致` | 25 个 `[InlineData]`，逐条核对 ID ↔ 名称 |
| `Create事件必须用FileObject当键_因为它根本没有FileKey` | ★ **直接拦住本缺陷**：`FileKey=0, FileObject=0x…` → `PrimaryKey` 必须是 `FileObject` 且非 0 |
| `Create事件若误用FileKey会导致键为0` | 反证：按"直觉"用 `FileKey` 当键，键恒为 0 |
| `订阅关键字必须包含CreateNewFile` | ★ 拦住第二个缺陷：`SUBSCRIBE_KEYWORDS & 0x1000 != 0` |
| `NameCreate事件必须用FileKey当键` | `PrimaryKey == FileKey` |
| `Write事件必须同时给出两个候选键` | `Keys == [FileObject, FileKey]` |
| `CreateNewFile必须产生NewFile动作` | 模式 A 的「仅新建」依赖它 |
| `Close只移除FileObject映射` | `SecondaryKey == 0`，不误删 `FileKey` |
| `DirEnum与DirNotify不得用于建立映射` | 防止把 `*.tmp` 这类模式写进映射表 |

> **已实测**：把 `Create` 改回用 `FileKey` 当键 → 2 个用例立刻红灯；
> 从订阅关键字里去掉 `CREATE_NEW_FILE` → `订阅关键字必须包含CreateNewFile` 立刻红灯。

**为什么以前没发现**：这段分发逻辑当时**直接写在 ETW 回调里**，需要管理员权限 + 真实 ETW 会话
才能执行，107 个测试一个都碰不到。**这是本缺陷最重要的教训**：
不是「测试不够多」，而是**被测的代码结构本身不可测**。
把纯逻辑从回调里抽出来之后，一条断言就能拦住。

### 缺陷 10：在 `OnHandleCreated` 里设 `ClientSize` → 卡片底部多出 39 px 空白

> 注：弹窗后来按 Win11 Fluent 风格重做过一次（圆角 8px / 柔和投影 / 文件名 + 文件夹按钮 /
> 关闭与链接的 hover 效果）。这条缺陷的**根因与回归用例一直保留** ——
> 只要布局是在 `OnHandleCreated` 里算的，无论外观怎么改都会多出这段空白。

**现象**（开发中由渲染探针发现，未流出）：自绘置顶窗内容只需 114 px 高，实际却是 153 px，
底部一条明显空白。

**根因**：布局（测量文字 → 设 `ClientSize`）原本写在 `OnHandleCreated` 里。
但**这个阶段窗口的非客户区尺寸还没定下来**，`Form.SetClientSizeCore` 会用
**旧的**非客户区差值去反算窗口大小：

```
Size = new Size(x + (Width - ClientSize.Width), y + (Height - ClientSize.Height));
                                            ↑ 此时 Height-ClientSize.Height = 39（默认窗体的旧值）
```

于是高度被多加 39 px。宽度恰好没受影响，所以只有纵向出问题，更不容易察觉。

**验证**：在句柄创建**之后**再设一次 `ClientSize`，值就正确了（114 不变）——
说明问题不是"算错了"，而是"设的时机不对"。

**修复**：把 `CreateFonts()` + `Measure()` 从 `OnHandleCreated` 移到 **`OnLoad`**。
`OnLoad` 在 `Show()` 内部、首次绘制之前触发，此时尺寸已经可靠，也不会闪一下。

**回归用例**：`AlertPopupLayoutTests.卡片必须精确贴合内容_外侧只留对称的投影留白`。
已实测：改回 `OnHandleCreated` 后立刻红灯（卡片外侧留白被多算，不再等于投影宽度）。

> **顺带说明为什么这个类必须存在**：`AlertPopup` 是**完全自绘**的顶层窗口 ——
> 没有子控件、没有布局引擎兜底，尺寸和文字位置全靠手算。
> 这类代码编译器和普通单元测试都覆盖不到，出问题只有肉眼能看见。
> 这次靠的是一个「把窗体渲染成 PNG 并打印各矩形坐标」的临时探针发现的 ——
> 探针发现了问题，测试把它固化下来。

### 缺陷 11：日期筛选显示成半截时间 `2026-10-12 09` + 打开窗口查不到任何记录

**现象**（用户反馈）：日志窗口的两个日期选择器显示成 `2026-10-11 09` / `2026-10-12 09`，
看着像坏掉的半截时间。用户明确要求**只到「天」**，显示 `2026-10-12` 就够。

**根因（两层）：**

**① 格式本来是 `yyyy-MM-dd HH:mm`，被宽度裁成了 `2026-10-12 09`。**
`DateTimePicker.Width` 是**原始像素**，不随 DPI 放大。而

```
125% DPI 下 "yyyy-MM-dd HH:mm" 文本本身就需要 128 px
+ 复选框（ShowCheckBox）约 25 px
+ 下拉按钮约 22 px
= 约 175 px  >  代码里写死的 150 px
```

所以时间部分被裁掉 —— 用户看到的 `2026-10-12 09` 是**截断结果**。
渲染对比可以直观看到：`Width=150` 时只剩 `2026-10-12 |`，`Width=190` 时完整。

**② 打开日志窗口默认查出空列表。**
`DateTimePicker.Checked` **默认就是 `true`**，而 `Value` 默认是 `DateTime.Now`，
旧代码又直接 `q.From = _dtFrom.Value` —— 于是查询区间变成
「From = 现在、To = 现在」，**什么都查不到**，必须点一次「重置条件」才正常。

**修复**：

| # | 修复 |
|---|---|
| 1 | 格式改为 **`yyyy-MM-dd`**（只到天），`ShowUpDown = false` 用日历下拉选日期 |
| 2 | 宽度改为**按字体实测计算**（`TimePickerWidth(font)`），不再写死 |
| 3 | `BuildQuery` 里按**整日**展开：`From = 该日 00:00:00`、`To = 该日 23:59:59.9999999` —— 这一步同时消掉了「From = To = 现在」的空列表问题 |
| 4 | 显式把默认区间设为**今天**（不依赖 `Checked` 的默认值） |
| 5 | 快捷按钮改为按天：**今天 / 昨天 / 最近 7 天 / 全部时间**（与"只到天"的语义一致） |

**回归用例**：`LogFormFilterLayoutTests`（4 个）。已双向验证有效：

| 临时改回 | 失败用例与报错 |
|---|---|
| 带时分的格式 + `Width=150` | `时间选择器必须只精确到天`、`时间选择器宽度必须放得下完整日期文本`（报「实际 150 px，至少需要 175 px」） |
| 去掉整日归一化 + 不显式设默认值 | `打开日志窗口时默认查询今天全天`（报 `Expected: 00:00:00 / Actual: 09:34:14` —— 正是"From = 现在"的空列表 bug） |

> **两个值得记的点：**
>
> 1. `DateTimePicker.PreferredSize` **不反映内容宽度**（只返回当前宽度），
>    所以不能用「`PreferredSize > Width`」这类通用检查发现裁切 ——
>    必须自己用 `TextRenderer.MeasureText` 量。第一次排查就是被这个绕了一圈。
> 2. **`DateTimePicker.Checked` 默认是 `true`**，这是个很容易踩的默认值。
>    配合 `Value` 默认 `DateTime.Now`，就会得到一个「From = To = 现在」的空查询。
>    凡是这种"默认值反直觉"的控件，都应该**显式设置**而不是依赖默认。

### 缺陷 12：CSV 公式注入（安全）

**现象**（安全审计发现，非用户报告）：导出的 CSV 没有任何公式注入防护。

**根因**：`Csv()` 只转义 `, " \n \r`，没有处理**以 `=` `+` `-` `@` 开头的单元格**。
Excel / WPS / LibreOffice 会把这类单元格当**公式求值**。

**为什么这里真的可利用**：导出字段里「进程名」是**攻击者可控**的 ——
把可执行文件重命名为 `=cmd|'/c calc'!A1.exe` 再运行它（并让它往 C 盘写点东西），
导出日志 CSV 后在 Excel 里打开就会执行。

**修复**：以 `= + - @ \t \r` 开头的字段前置一个单引号（表格软件按纯文本处理，单引号本身不显示）。

**回归用例**：`EventLogStoreExportTests.CSV导出必须中和公式注入`。

### 缺陷 13：导出被静默截断到 5000 条（数据丢失）

**现象**（安全审计发现）：`ExportCsvAsync` / `ExportJsonAsync` 都写着 `query.Limit = 100_000`，
但 `QueryAsync` 里是 `Math.Clamp(q.Limit, 1, 5000)` —— 导出实际只拿得到 5000 条。
更糟的是提示会说「已导出 5000 条」，用户以为导全了。

**根因**：**导出与分页共用了同一个上限钳制值**。分页需要 5000 的上限防内存爆，
导出需要的是"尽量全"。

**修复**：拆成两个常量（`MaxPageSize = 5000` / `MaxExportRows = 200_000`），
`QueryAsync` 走分页钳制，导出走 `QueryForExportAsync`。顺带去掉 `query.Limit = …` 这个**隐式副作用**
（它当时直接改动了调用方传入的对象）。

**回归用例**：`EventLogStoreExportTests.导出不得被截断到5000条`（插入 5001 条验证）
与 `分页查询仍必须限制在5000条以内`。

### 缺陷 14：`Keys` 迭代器在热点路径上分配（性能回归）

**现象**（自查发现）：为了给 `KernelFileEventRoute` 提供"两个键"的遍历，
写了 `public IEnumerable<ulong> Keys { get { yield return … } }`。
**迭代器每次 `foreach` 都会分配一个 enumerator 对象。**

**为什么这次很严重**：这条路径在处理**被排除的写入**时也会走到
（`HandleWrite` 里判定为排除后要 `MarkExcluded`），而排除路径占写入事件的 **90% 以上**，
设计上明确要求"零分配丢弃"。

**修复**：改成**结构体枚举器**（`KeyPair` + 嵌套 `Enumerator`），
`foreach` 在编译期走 `GetEnumerator/MoveNext/Current`，不装箱、不分配。调用点完全不变。

**回归用例**：`遍历路由键不得产生堆分配` —— 用 `GC.GetAllocatedBytesForCurrentThread()`
实测 10 万次遍历的分配量。已实测：改回 `IEnumerable` 版本时该用例报
**「100000 次遍历分配了 8000000 字节」**（每次 80 字节的迭代器）。

> **修复过程中被测试抓到一次**：结构体枚举器第一版在 `primary == 0` 时
> `MoveNext` 会直接返回 `false` 而漏掉 `secondary` ——
> 现有用例 `Write事件缺一个键时不应重复计数` 立刻红灯。改成在构造函数里
> 就确定"第一个有效键/第二个有效键"后修复。

### 缺陷 15：排除规则的通配符转正则存在灾难性回溯（ReDoS）

**现象**（安全审计发现）：`ExclusionMatcher.BuildRegex` 把通配符逐字符转正则
（`*` → `.*`，其余字符 `Regex.Escape`），但**不折叠连续的 `*`**。
于是配置里写 `**********` 会生成 `^.*.*.*.*.*.*.*.*.*.*$` ——
匹配失败时正则引擎要枚举所有切分方式，**代价随 `.*` 个数指数上升**。

**为什么这条影响面不小**：排除匹配跑在 **ETW 热点路径**上（每个文件写入事件都过一遍），
而进程在精确模式下是**管理员权限**。一个手滑写错、或被人改过的配置文件
（`%AppData%` 是同用户可写的）就能把 CPU 挂住。

**修复（两道防线，缺一不可）**：

| # | 防线 | 解决什么 |
|---|---|---|
| 1 | 编译时**折叠连续的 `*`** | 连续星号（`**` 与 `*` 语义等价） |
| 2 | `WildcardRegex`：**50ms 匹配超时** + **超时后永久熔断该条规则** | 交替星号（`*a*a*a*` 折叠不掉） |

> 第 2 条里「永久熔断」是关键：只加超时的话，每个文件事件都要白等一次 50ms，
> **仍然是 DoS**。熔断后该规则直接失效，后续匹配瞬间返回。

**实测数据**（`%TEMP%\redos-probe`）：

| 正则形状 | 输入 | 耗时 |
|---|---|---|
| 扁平 `^.*a.*a.*a.*a.*a.*a.*a.*ab$`（通配符能生成的形状） | 40 字符 | **1641 ms** |
| 嵌套量词 `^(a+)+$`（通配符生成不出来，对照组） | 29 字符 | 超时（3s） |

**回归用例**（3 个，追加到 `ExclusionMatcherTests`）：
`排除规则里的连续星号必须被折叠`（结构性断言：编译出的正则不得含 `.*.*`）、
`连续星号的匹配结果必须与单个星号完全一致`、
`交替星号的病态规则必须被超时熔断而不是挂住`。

> **★ 这个测试差点形同虚设，值得单独记一笔**：
> 第一版把阈值写成 `Assert < 2000ms`，结果「把超时去掉也照样通过」——
> 因为实测耗时是 **1641 ms**，刚好卡在阈值下面。
> **阈值太松 = 测试没有鉴别力。** 收紧到 300 ms 后才成立：
> 有超时 ~55 ms 通过，无超时 **1751 ms 红灯**。
>
> 教训：**性能类断言必须用实测值倒推阈值**，不能凭感觉给一个"看起来够宽松"的数。

### 缺陷 16：改成分层窗口后文字变模糊（我自己的判断失误）

**现象**（用户反馈）：置顶弹窗的字体"很模糊，看不清"，并强调**最初是清晰的**。

**排查路径**（几次都判错，值得完整记下来）：

| 步骤 | 假设 | 结论 |
|---|---|---|
| 1 | 灰度抗锯齿（`AntiAliasGridFit`）偏软 | **不成立** —— 受控实验里灰度与 ClearType **都清晰** |
| 2 | 位图 DPI（96）与测量 DPI（120）不一致 | **判错了** —— DPI 感知进程里 `new Bitmap(...)` 默认就是屏幕 DPI，`SetResolution` 是空操作 |
| 3 | 文字栅格化引擎本身有问题 | ✅ **找到了** |

**真正的根因**：为了做"卡片外侧透明"，窗口改成了分层窗口（`UpdateLayeredWindow`）。
但绘制文字仍然用 **GDI 的 `TextRenderer.DrawText`** ——
**GDI 的 ClearType 在带 alpha 通道的 32bpp 位图上会退化成「无抗锯齿」**，
文字变成又粗又硬的块状。

**定位方法**：把「位图 DPI × 抗锯齿方式 × 绘制 API」排成 7 种组合各渲染一张，放大对比：

| 组合 | 效果 |
|---|---|
| GDI `TextRenderer` + **ClearType** | ❌ **块状、无抗锯齿** |
| GDI `TextRenderer` + `AntiAlias` | ✅ 干净锐利 |
| GDI+ `DrawString` + **ClearType** | ✅ **有真实次像素彩边（与最初效果一致）** |
| GDI+ `DrawString` + `AntiAlias` | ✅ 锐利 |

**修复**：文字测量与绘制**整体切到 GDI+ 管线**
（`Graphics.MeasureString` / `Graphics.DrawString`），
测量与绘制必须是同一个引擎，否则布局与实际字形会有偏差。

**顺带修掉一个同源的坑**：GDI+ 的 `MeasureString` **默认不把行尾空格算进宽度**，
而混排那行靠 `"  写入了  "` 的空格制造间距 → 测量偏窄 → `"写入了"` 与 `"24 MB"` 贴在一起。
加 `StringFormatFlags.MeasureTrailingSpaces` 解决。

**回归用例**：`文字测量必须把行尾空格计入宽度`（去掉该 flag → 报 `"写入"=34，"写入  "=34`）。

> **★ 这次最值得记的不是修复，而是「测试宿主不是 DPI 感知的」这件事**：
> 前面几轮我在 `dotnet xxx.dll` 下做验证，`DeviceDpi` 一直是 96 ——
> **在 125% 的真实环境里根本复现不了问题**，白跑了几轮。
> 必须在测试项目里用 `[ModuleInitializer]` 调
> `SetProcessDpiAwarenessContext(PerMonitorV2)` 把宿主提升为 DPI 感知（实测 96 → 120），
> 验证才有意义。**验证环境与被验证环境不一致，等于没验证。**

### 缺陷 17：事件丢失对用户完全不可见（两种模式都有）

**现象**（GitHub 同类项目调研时发现，非用户报告）：采集侧丢了事件，用户不可能知道。

| 模式 | 修复前 |
|---|---|
| 标准模式 | `ReadDirectoryChangesW` 缓冲区溢出（`ERROR_NOTIFY_ENUM_DIR`）**有计数**（`_resync`），但该计数**从未在任何界面或诊断里显示** —— 只在一处测试的失败信息里用过 |
| 精确模式 | `EVENT_TRACE_PROPERTIES.EventsLost` 字段**定义了却从未被读取**，连计数都没有 |

**为什么这条最严重**：本工具的全部价值就是「如实告诉你 C 盘被写了什么」。
少记了事件却不提示，用户会**以为看到的是全部** ——
这比直接报错糟得多，也正是本项目文档反复强调的「静默失败」类型。

**旁证**：`wtrace`（697 星，同为 C# + ETW）的 README 专门有一节
`WARNING: … events were lost in the session.`，说明原因并给处置建议。成熟工具会说这件事。

**修复**：

| # | 改动 |
|---|---|
| 1 | `CollectorStats.ResyncCount` → **`LostEvents`**，统一两种模式的语义（标准模式=溢出**次数**，精确模式=丢失**条数**），注释写清差别 |
| 2 | 精确模式新增**周期性 `ControlTrace(QUERY)`**（30 秒一次，`Stop()` 前再补一次）读 `EventsLost` + `RealTimeBuffersLost`。**这两个计数器只存在于 `EVENT_TRACE_PROPERTIES` 里，QUERY 是唯一读取途径** |
| 3 | 统计链路从「挑 3 个字段的元组」改成**整块传 `CollectorStats`**，以后加字段不用改签名 |
| 4 | 三处显示：设置页运行统计（带人话解释）、托盘提示（`· 丢 N`）、诊断导出 |

**回归用例（3 个，全部双向验证）**：

| 用例 | 改回去的后果 |
|---|---|
| `采集器报告的丢失事件必须出现在快照里` | 漏接 → `Expected: 123 / Actual: 0` |
| `EVENT_TRACE_PROPERTIES_必须是120字节且关键偏移正确`（扩充 `EventsLost@88` / `RealTimeBuffersLost@100`） | 对调字段顺序 → `Expected: 88 / Actual: 92` |
| `运行统计必须完整显示且包含丢失事件` | 删掉那一行 → `Sub-string not found` |

> **★ 为什么偏移断言特别重要**：结构体偏移错了**不会报错**，
> 只会静默读到垃圾值（表现为计数乱跳或永远为 0）——
> 那比根本没有这个功能更糟，因为它看起来像「一切正常」。

> **修复过程中注意到的并发点**：`ControlTrace(QUERY)` 与 `Stop()` 都会写同一块
> `_propsBuffer`，所以加了 `_propsLock`；定时器在 `Stop()` 里先停再停会话，
> 避免查询到已停止的会话。

### 教训

这十七个缺陷都满足「**编译通过 + 单元测试全绿 + 运行时明显坏掉**」。

| 失败模式 | 需要什么才能覆盖 |
|---|---|
| 依赖真实句柄 / 内核通知 / 时序（缺陷 1、2） | 集成测试 |
| 依赖真实窗体 / DPI / 字体度量（缺陷 3、4） | 界面冒烟测试 |
| **完全自绘、没有布局引擎兜底（缺陷 10）** | **渲染探针 + 界面冒烟测试** |
| **控件宽度写死、不随 DPI 缩放（缺陷 11）** | **界面冒烟测试 + 自己量文本宽度** |
| **攻击者可控数据进入导出/命令行（缺陷 12）** | **安全审计 + 端到端导出测试** |
| **上限/常量被两处共用（缺陷 13）** | **越过边界的测试（5001 条）** |
| **热点路径上的隐式分配（缺陷 14）** | **实测分配量的测试** |
| **可写配置喂给正则引擎（缺陷 15）** | **实测耗时的测试（阈值必须卡紧）** |
| **换了渲染路径、底层 API 语义随之改变（缺陷 16）** | **受控对照实验（把变量排成矩阵）+ 渲染探针** |
| **数据悄悄少了、界面却显示一切正常（缺陷 17）** | **对照同类项目 + 结构性断言（含结构体偏移）** |
| 依赖真实运行数据才暴露（缺陷 5、8、9） | **看真实运行数据**（`events.db` / 诊断导出） |
| 依赖特定权限 / 特定配置路径（缺陷 6、7） | 跑一次真实调用 |
| **逻辑本身不可测（缺陷 9 的结构性原因）** | **先重构出纯函数，再写测试** |

**缺陷 8 和 9 是串联的**：8 让 schema 解析正常，才让 9 暴露出来；
而 9 又是 8 引入的**诊断导出功能**定位的 —— 这印证了一件事：
**给程序加一个「把内部状态吐出来」的出口，回报率极高**。

**缺陷 9 的特殊价值**：它证明了「测试覆盖率」这个指标本身有欺骗性。
当时 107 个测试全绿、构建 0 警告，但精确模式**功能上是完全死的**。
真正的问题不是覆盖率不够，而是**关键逻辑放在了一个测不到的位置**。

**缺陷 10 补上了另一块**：界面冒烟测试能测「有子控件、有布局引擎」的窗体
（缺陷 3、4），但对**完全自绘**的窗口无能为力 —— 那种情况下
「把窗体渲染成图片 + 打印内部坐标」的临时探针是唯一手段。
探针负责**发现**，测试负责**固化**，两者缺一不可。

**关于「静默失败」的通用教训**（缺陷 1、2、6、7、8、9 都是这一类）：
Windows API 大量存在「**不抛异常、不返回错误、但什么也没做**」的行为 ——
`Show()` 不报错但通知被丢弃、`StartTrace` 返回一个看不懂的错误码、
`TgtGetEventInformation` 返回垃圾字段名。
**唯一的对策是把「预期值」写成断言**（结构体尺寸/偏移、订阅关键字、
通道发送计数），让"什么都没发生"变成一个可见的红灯。
