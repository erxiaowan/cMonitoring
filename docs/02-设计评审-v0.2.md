## 一、阈值判定口径（对应问题 1）

### 1.1 为什么"单次 IRP"绝对不能作为口径

`IRP_MJ_WRITE` 的长度受 `MaximumWriteLength` 与 Cache Manager 的分段策略限制。一次 100 MB 的 `WriteFile` 会被拆成几十到上百个 IRP（典型 1 MB 或更小，取决于硬件与文件系统驱动）。

**若按"单个 Write 事件 Size ≥ 10 MB"判定，100 MB 的文件保存一次都不会触发** —— 这在用户眼里就是"工具完全没用"。这是必须在设计阶段掐死的坑。

### 1.2 三种口径定义

| 口径 | 定义 | 典型场景 | 默认 |
|---|---|---|---|
| **P1** 单次 IRP | 单个 `Write` 事件的 `Size` ≥ 阈值 | 少见（仅大块直写） | 否 |
| **P2** 同文件窗口累计 | 同一 `FileKey` 在时间窗口内累计写入 ≥ 阈值 | 保存大文件、下载、解压 | **✅ 默认** |
| **P3** 同进程窗口累计 | 同一 PID 在时间窗口内累计写入 ≥ 阈值 | 批量小文件写入 | 可选开关（**语义不同，见 1.6**） |

### 1.3 【关键增强】Offset 连续性归并 —— 比时间窗口更准

`Write` 事件携带 `Offset`。据此可以把被拆散的 IRP **还原成一次逻辑写入**：

```
归并条件（三者同时满足）：
  1. 相同 FileKey
  2. 相同 IssuingThreadId
  3. Offset_{n+1} == Offset_n + Size_n     ← 首尾相接
  且 两次事件间隔 < 200 ms
```

- **为什么必须按 `IssuingThreadId` 分组**：多线程并发写同一文件时，Offset 会交错，不分组会导致归并链断裂。
- **归并后的 `Size` 就是逻辑写入量**，直接与阈值比较。
- **兜底**：若 Offset 不连续（交错写、随机写、覆盖写），退化为 P2 的时间窗口累计。

> **最终判定公式**：`触发 = (Offset归并后的逻辑写入量 ≥ 阈值) OR (窗口内累计 ≥ 阈值)`

### 1.4 窗口实现：固定窗口（tumbling），不是真滑动窗口

真滑动窗口需要为每个文件维护时间戳队列 —— 内存与 CPU 都不划算（20 万个文件 × 队列）。

改用 **固定窗口 + 分桶**：

```
状态：FileKey -> (WindowStartTick, AccumulatedSize)
事件到达：
  if (now - WindowStartTick >= WindowMs) { WindowStartTick = now; AccumulatedSize = 0; }
  AccumulatedSize += Size;
```

- 成本 O(1)、零分配。
- 语义差异：跨桶边界的连续写入可能被切成两个桶。**这个缺口由 1.3 的 Offset 归并覆盖**，两者互补。

### 1.5 阈值层与节流层的职责分离（重要）

这两件事容易混淆，必须分开：

| 层 | 职责 | 触发后的动作 |
|---|---|---|
| 阈值层 | 判定"是否超过 10MB/50MB" | **立即重置窗口**，允许同一文件再次触发 |
| 节流层 | 判定"是否值得打扰用户" | 文件级 60s / 进程级 30s / 全局令牌桶 |

如果只在阈值层做"标记已触发不重置"，会导致一个持续写入的大文件只提醒一次，用户以为工具停了。如果只重置不做节流，会刷屏。**两层各司其职。**

### 1.6 P3 口径的语义澄清（对用户提案的修正）

用户提案里的口径 3（同进程 5 秒累计 50MB）与口径 2 **语义完全不同**：

- P2 = "**某个文件**被连续写入了 50MB"
- P3 = "**某个进程**在 5 秒内总共写了 50MB"，可能是 500 个 100KB 的小文件

P3 不该被称作"单次写入超过 50MB"，它应该叫 **"进程突发写入"**。建议：

- P3 作为**独立开关**（默认关），而不是阈值口径的选项之一。
- UI 文案区分：模式 B/C 的说明里只提 P2；P3 单独放在"高级 · 进程突发告警"。
- 理由：P3 触发频率远高于 P2，默认开启会显著增加噪音。

### 1.7 UI 文案（必须原样出现，不允许简写）

| 位置 | 文案 |
|---|---|
| 设置页模式 B 说明 | 同一文件在 1 秒内累计写入超过 **10 MB** 时提醒（按逻辑写入量，非单次 IRP） |
| 设置页模式 C 说明 | 同一文件在 1 秒内累计写入超过 **50 MB** 时提醒（按逻辑写入量，非单次 IRP） |
| 通知正文 | `[模式 B] 1 秒累计 12.4 MB · 精确` |
| 高级折叠区 | 可切换判定口径（P1 单次 IRP / P2 同文件窗口 / P3 进程突发） |
| 阈值配置 | 10 / 50 MB 为默认值，**可自定义**，不硬编码 |

## 二、FileKey → Path 映射（对应问题 2）—— 精确模式最大难点

### 2.1 事件字段现实

| 事件 | 携带字段 | 用途 |
|---|---|---|
| `Create` | `FileKey`, `FileObject`, `FileName`(完整), `IssuingThreadId` | **建立映射** |
| `Write` | `FileKey`, `FileObject`, `Offset`, `Size`, `IssuingThreadId`, `Flags` | 核心判定 |
| `Close` | `FileKey`, `FileObject` | **移除映射** |
| `Rename` | `FileKey`, `FileObject`, `FileName`(新路径) | **更新映射** |
| `SetEndOfFile` | `FileKey`, `FileObject`, `EndOfFile` | 辅助（截断检测） |

> **关键简化**：`EVENT_HEADER.ProcessId` 是每个事件都自带的，**进程名不需要反查线程**。这砍掉了原设计中"线程 ID → PID"的转换环节。

### 2.2 映射表结构

```
FileKey (128-bit) → PathEntry {
    string Path;          // 规范化后的 C:\... 形式；null = 未知；"" = 已排除
    long   LastAccessTick;
}
```

- 处理层是**单消费者线程**，所以用普通 `Dictionary<FileKey128, PathEntry>` 即可，**无锁**。
- `FileKey128` 用 `readonly struct` 实现 `IEquatable`，避免装箱。

### 2.3 生命周期规则（6 条）

1. `Create` → 写入映射（含路径规范化）。
2. `Close` → **立即移除**（防 FileKey 重用污染新文件）。
3. **但 `Close` 不保证到达** —— 进程被强杀、系统关机、驱动持有句柄时不会有 `Close` 事件。所以不能只依赖 Close。
4. **TTL + LRU 双保险**：TTL = 5 分钟（可配），容量上限 = 20 万条（可配）。超时或超限时淘汰最久未访问的条目。
5. 映射缺失 → 路径标记为"未知"，**记入日志与统计，但不弹窗**（避免噪音风暴）。
6. UI 实时显示 **"路径映射命中率 98.7%"**，让用户知道精确模式的实际效果。

### 2.4 无法解决的缺口（必须写进"已知限制"）

**程序启动之前就已打开的长期句柄**（数据库文件、日志文件、正在下载的大文件、虚拟机磁盘）永远不会有 `Create` 事件 → **永久显示"未知路径"**。

- 缓解 1：启动引导提示"建议开机后尽早启动本工具以获得最佳路径映射率"。
- 缓解 2：设置页提供"重启监控"按钮（重新建立映射，代价是丢失已有映射）。
- **不采用**：启动时全盘枚举建立初始映射 —— 几十万文件 × 数秒至数分钟，违反启动性能要求。

### 2.5 路径规范化管线

```
原始：\Device\HarddiskVolume3\Users\alice\a.txt
  ↓ 卷设备名 → 盘符（QueryDosDevice，建表并缓存）
  ↓ 剥离 \\?\ 与 \??\ 前缀
  ↓ 统一分隔符为 \
结果：C:\Users\alice\a.txt
```

- **比较**：`OrdinalIgnoreCase`，**不额外保存大写副本**（省一半内存）。
- **显示**：保留原始大小写。
- **长路径**：`app.manifest` 开启 `longPathAware`，支持 > 260 字符。

### 2.6 内存优化（关键，否则吃掉 1/4 内存预算）

朴素做法：20 万条路径 × 平均 80 字符 × 2 字节 ≈ **32 MB**，直接吃掉 150MB 预算的 21%。

优化两步：

1. **路径驻留（interning）**：相同路径字符串只存一份，映射表存引用。
2. **排除路径立即释放**：判定为排除路径后，**立刻把 `Path` 置为 `""` 并释放字符串**，只保留 `FileKey → 已排除` 的标记。

效果：长期驻留的只有**非排除路径**（通常几千条），内存降至 **< 2 MB**。

> 注意顺序：必须先构造路径才能做排除判定，所以峰值时仍会短暂持有字符串。这没关系，GC 会回收。

### 2.7 性能预算

| 环节 | 目标 |
|---|---|
| 单事件解析（不含路径构造） | < 1 μs |
| 路径构造 + 规范化 | < 5 μs |
| 事件头解析 | `Span<byte>` 零拷贝，不 new 对象 |
| 字符串分配 | 仅在 `Create` 事件时发生，`Write` 事件**零分配** |

## 三、自身写入排除（对应问题 3）

### 3.1 主防线：按 PID 排除（调整用户提案的优先级）

每个 ETW 事件头自带 `EventHeader.ProcessId`。处理层的**第一行代码**就是：

```
if (header.ProcessId == Environment.ProcessId) return;
```

**这一条比任何路径规则都可靠** —— 它不依赖路径规则是否写对、不依赖路径映射是否命中。成本接近 0。

用户提案把路径排除放在第一位、进程排除放在第二位，建议调换：**PID 是第一道闸门，路径是双保险。**

### 3.2 路径层（双保险）

```text
%AppData%\CWriteWatcher\*
%LocalAppData%\CWriteWatcher\*
%AppData%\..\Local\Temp\CWriteWatcher\*     ← 导出临时文件
<安装目录>\*                                 ← 若将来有安装程序
```

- **必须覆盖 SQLite 的 `-wal` 与 `-shm` 文件**（WAL 模式下会持续写入）。排除整个目录即覆盖。
- 导出文件：导出到用户选择的目录时，**临时豁免**（不弹窗但记日志）—— 导出是用户主动行为，弹窗只会造成困惑。

### 3.3 容易漏掉的循环源（对用户提案的补充）

| 源 | 路径 | 处理 |
|---|---|---|
| Toast 通知历史 | `%LocalAppData%\Microsoft\Windows\Notifications\*` | **新增默认排除** |
| Windows 事件日志 | `C:\Windows\System32\winevt\Logs\*` | **新增默认排除** |
| 崩溃转储 | `%LocalAppData%\CrashDumps\*` | 已在排除表 |
| 程序自身日志/配置 | `%AppData%\CWriteWatcher\*` | 见 3.2 |

> 第 1 条尤其隐蔽：**我们弹 Toast → Windows 写通知历史 → 触发监控 → 再弹 Toast**，形成二级循环。必须在默认排除表里。

### 3.4 丢弃位置

处理层**第一行**（PID 判定）即丢弃，**绝不进入阈值判定与节流层**，避免任何无谓开销。

## 四、单实例与权限模型（对应问题 4）

### 4.1 MVP 决策：单进程单模式

- **同一时间只运行一种模式**，不做"普通 UI + 高权限后台"双进程。
- 切换模式 → 提示"需要重启程序" → 用 `ShellExecute(runas)` 提权重启。
- 用户取消 UAC → **保持原模式，不修改配置**（避免配置与实际运行状态不一致）。
- 理由：双进程方案要处理命名管道 ACL、UIPI、配置读写竞争、生命周期同步，复杂度远超本项目定位。

### 4.2 单实例：`Local\` Mutex

- 名称：`Local\CWriteWatcher.SingleInstance.{用户SID}`
- 用 `Local\`（session 作用域）而非 `Global\`：
  - 普通用户创建 `Global\` 对象可能被 ACL 拒绝。
  - 多用户同时登录时，**每个会话各跑一个托盘程序是正确行为**（托盘是 per-session 的）。
- 加用户 SID 后缀是为了同一会话内多用户切换场景的隔离。

### 4.3 【重要坑】跨权限唤起会失败

精确模式（管理员进程）与普通用户进程**在同一个 session**，所以 `Local\` Mutex **能**检测到冲突。但：

> **UIPI（用户界面特权隔离）会阻止普通进程给管理员窗口发消息** → "二次启动唤起设置窗口"在跨权限时必然失败。

降级处理：检测到已运行但唤起失败 → 只弹一个消息框"程序已在运行（请查看系统托盘）"，不要静默失败让用户困惑。

### 4.4 【重要坑】自启项切换必须"先删后写"

| 模式 | 自启位置 |
|---|---|
| 标准模式 | `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` |
| 精确模式 | 任务计划程序 `/SC ONLOGON /RL HIGHEST` |

**切换模式时，如果只写新项不删旧项，两个自启项会同时存在** → 开机启动两次 → 第二个实例虽然会被 Mutex 挡住，**但 UAC 提示已经弹出来了**。用户体验灾难。

实现约束：

```
SetAutoStart(mode):
    RemoveAutoStart(Run);        // 无条件先删两个
    RemoveAutoStart(TaskPlan);
    AddAutoStart(mode);          // 再写目标那个
```

- 退出程序与卸载时，**两个位置都要清理**，避免残留。
- 提供"重置配置与自启项"入口，作为用户手动清理的兜底。

### 4.5 长期架构（v0.3 预留，MVP 不实现）

管理员 Windows Service（`LocalSystem`）+ 普通用户托盘 UI，通过**受限命名管道**（管道 ACL 允许当前用户）通信。

优点：
- UI 不需要管理员权限（避开 UIPI 问题）。
- 采集进程可开机即启（早于用户登录）→ **路径映射命中率大幅提升**，直接缓解 2.4 的缺口。

MVP 的接口设计需为此预留：**采集层与 UI 层只通过事件流耦合**，不共享内存状态。

## 五、默认监控范围修订（对应问题 5）

### 5.1 精确模式（推荐）

| 项 | 值 |
|---|---|
| 默认范围 | **整个 `C:\`** |
| 实现 | 单个 ETW 会话，无句柄爆炸问题 |
| 排除表 | **默认强制启用**；用户关闭时给出强警告 |
| 性能影响 | 无额外句柄；CPU 由事件量决定，已有降级机制 |

### 5.2 标准模式（免管理员降级）

| 项 | 值 |
|---|---|
| 默认范围 | `C:\Users\<当前用户>` 全递归<br>`C:\ProgramData` 全递归<br>`C:\Program Files`、`C:\Program Files (x86)`、`C:\Windows` **仅前 2 层** |
| UI 提示 | 设置页顶部常驻："**标准模式未覆盖全盘**（深层系统目录未监控）" |
| 全盘选项 | 提供"全盘监控"勾选，勾选时弹警告对话框（见 5.3） |
| 缓冲区 | 默认 64 KB；全盘模式建议 256 KB |
| 枚举方式 | **后台线程 + 进度条**，绝不阻塞 UI |

> **为什么默认要加 `Program Files` / `Windows` 的浅层**：用户原话是"如果有新的内容被写入 C 盘"。只监控 `Users` + `ProgramData` 会让用户觉得"我装了软件它没反应"。浅层覆盖能捕捉到安装、更新这类高价值事件，同时避免深层递归的句柄成本。

### 5.3 全盘模式警告内容

勾选"标准模式 · 全盘监控"时，必须先展示：

```
全盘监控将递归枚举 C:\ 下的所有目录，预计：
  · 目录数：约 120,000 ~ 400,000 个
  · 打开的目录句柄：同等数量
  · 首次枚举耗时：约 30 秒 ~ 3 分钟
  · 内存增量：约 80 ~ 200 MB（可能超过 150 MB 目标）
  · 句柄上限风险：需要调整进程句柄配额，可能失败

建议：改用「精确模式」实现全盘覆盖（需一次管理员授权，资源占用低得多）。
                                        [改用精确模式]  [仍然全盘监控]
```

### 5.4 【新增】覆盖率实时反馈 UI

设置页显示实时统计，让用户确信工具在工作：

```
当前状态
  监控目录      12,483 个
  打开句柄      12,483 个
  路径映射命中率  98.7%
  今日丢弃事件   0 条
  当前降级级别   L0 正常
```

这一条同时解决了"用户觉得没生效"和"用户不知道是否漏报"两个问题。

### 5.5 排除表始终可编辑

- 内置默认排除表（v0.1 §4.5）**默认全选启用**，用户可逐条禁用或添加自定义规则。
- 支持 `*` 通配与目录前缀匹配，大小写不敏感。
- 提供"恢复默认排除表"按钮。

## 六、资源指标与自动降级（对应问题 6）

### 6.1 指标重定义（v0.1 的写法会直接导致验收失败）

| 指标 | v0.1（错误） | v0.2（正确） |
|---|---|---|
| CPU | 保证 < 2% | **目标** 均值 < 2%，允许短时峰值 |
| 内存 | 保证 < 150 MB | **目标** 稳态 < 150 MB，超限时主动裁剪而非崩溃 |

### 6.2 CPU 测量口径（必须先定义，否则验收必扯皮）

- 采样：`Process.TotalProcessorTime` 差值 ÷ 采样间隔。
- **显示口径**：**占整机 CPU 百分比** = 单核占用 ÷ `Environment.ProcessorCount`。
  - 多核机器上这更符合用户直觉（任务管理器也是这个口径）。
- 配置项与验收标准**使用同一口径**，并在文档中显式写明。
- 采样间隔：2 秒（避免测量本身产生开销）。

### 6.3 四级自动降级（分级 + **可恢复**）

| 级别 | 触发条件 | 行为 |
|---|---|---|
| **L0 正常** | CPU < 2% | 全功能 |
| **L1 轻载** | 2% ≤ CPU < 10% 持续 5s | 扩大聚合窗口，合并提醒 |
| **L2 重载** | CPU ≥ 10% 持续 10s | 暂停模式 A；只保留 B/C；丢弃未达阈值的事件 |
| **L3 风暴** | Channel 积压 > 80% 容量 | `DropOldest` 丢弃，只保留超阈值事件 |

**【关键】恢复机制**（用户提案未覆盖，但不加就是永久降级）：

```
CPU < 2% 持续 30 秒 → 逐级恢复：L3 → L2 → L1 → L0
```

否则一次 Windows Update 全盘扫描就会让工具**永久停留在 L2**，之后所有普通写入都不再提醒，用户完全察觉不到。

### 6.4 降级必须留痕

- 记录每次进入/退出降级的时间、级别、丢弃事件数。
- UI 显示："**已降级至 L2 · 已丢弃 12,483 条事件**（点击查看原因）"。
- 原因页面列出当时的 CPU、事件速率、Top 5 事件来源进程。
- 这一条是"工具为什么没提醒我"这个问题的唯一答案，**不能省**。

### 6.5 内存超限的行为

- 超过 150 MB → 触发日志表**激进裁剪**：保留条数减半 + `VACUUM`。
- **绝不崩溃、绝不拒绝服务、绝不静默失败**。

### 6.6 【产品层建议】比降级更根本的做法

**模式 A 默认只对"新建文件"提醒，不对"修改已有文件"提醒。**

- 理由：用户原话是"**如果有新的内容被写入 C 盘**"，语义上更接近"新文件"。
- 而"修改已有文件"在 `C:\Users` 下**每秒都在发生**（浏览器缓存、IDE 自动保存、编辑器临时文件、同步盘）→ 模式 A 开着本质就是通知风暴制造机，即使有排除表也挡不住。
- 实现：模式 A 只响应 `Create` 事件（`FILE_ACTION_ADDED`），忽略 `Write` 到已存在文件的事件。
- 提供高级开关"包含修改已有文件"，**默认关闭**。
- 模式 A 开启时给出警告："此模式可能产生较多提醒"。
- **建议出厂默认模式为 B（10 MB）而非 A** —— 开箱体验差距巨大。
