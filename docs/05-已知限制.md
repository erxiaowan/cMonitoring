# 已知限制

> **使用前请务必阅读。** 本文档如实列出本工具**做不到**的事情。
> 其中一部分是 Windows 用户态的根本约束（换任何实现都绕不过），另一部分是本次的工程取舍。

阅读建议：先看最后一节的[速查表](#九速查表)，再按需展开对应条目。

## 一、采集能力限制

### 1.1 用户态无法「免管理员 + 精确单次写入字节」

**这是整个项目最重要的限制，也是双模式架构存在的唯一原因。**

Windows 用户态能拿到的文件变更接口只有两个：

| 接口 | 能拿到 | 拿不到 |
|---|---|---|
| `ReadDirectoryChangesW` | 哪个文件被改了、改了哪个属性 | 长度、偏移、发起进程 |
| USN Journal | 变更序号、原因标志 | 长度、偏移、发起进程 |

「某进程在偏移 X 处写入 Y 字节」这个信息只存在于文件系统驱动栈的 `IRP_MJ_WRITE` 里。
用户态唯一的正规读取渠道是 ETW 的 `Microsoft-Windows-Kernel-File` provider —— 而它**需要管理员权限**。

**影响**：标准模式的「写入大小」永远是估算值，UI 上以 `≈ 12.4 MB` 标注。
**建议**：需要精确值就切精确模式；只是想知道"谁在往 C 盘写大文件"，标准模式够用。

### 1.2 标准模式无法归因到进程

`ReadDirectoryChangesW` 的通知里没有进程信息。

**影响**：标准模式下所有事件的 `ProcessId = 0`、`ProcessName = null`，提醒里**无法显示是哪个程序写的**。
**建议**：这是需求里"提醒内容包含进程名"在标准模式下无法满足的部分，需要进程名就必须用精确模式。

### 1.3 标准模式对「原地覆盖写」漏报

差分估算靠的是"文件大小变了多少"。如果一个程序在**不改变文件大小**的情况下覆盖写（例如数据库就地更新某一页、`SetFilePointer` 后覆写已有区间），文件大小不变 → 差分值为 0 → **不触发**。

**影响**：数据库类程序（SQLite、SQL Server、各种嵌入式 DB）的大块写入在标准模式下基本检测不到。
**建议**：这类场景必须用精确模式。

### 1.4 标准模式缓冲区溢出会丢事件

`ReadDirectoryChangesW` 的内部缓冲区在事件速率超过消费速率时会溢出，返回 `ERROR_NOTIFY_ENUM_DIR`，此时**无法得知丢了多少、丢了什么**。

**影响**：程序计数里的 `ResyncCount` 会增长，表示"这段时间的通知不可信"。
**建议**：状态页看到 `ResyncCount` 持续增长，说明监控范围过大或写入过密，应缩小范围。

### 1.5 标准模式全盘监控会句柄爆炸

`ReadDirectoryChangesW` 必须**一个目录一个句柄**。全盘 C: 通常有 10 万 ~ 40 万个目录。

**影响**：内存和句柄数都会爆掉，远超 150 MB 预算；枚举本身也要数秒到数十秒。
**建议**：程序默认在标准模式下只监控 `C:\Users\<当前用户>` + `C:\ProgramData`，并在 UI 上明确提示"标准模式未覆盖全盘"。要全盘覆盖请用精确模式（单 ETW 会话，无此问题）。

> 程序在枚举阶段会跳过命中排除表的目录子树（`WinSxS`、`SoftwareDistribution`、`Packages` 等），可省下数千个句柄，但这只是缓解，不能根治。

### 1.6 差分估算的其它失真来源

即使文件大小变了，差分值也可能不等于真实写入量：

| 场景 | 失真 |
|---|---|
| 程序先 `SetEndOfFile(0)` 再重写 | 估算值偏小（被当成"新文件"从头算） |
| 多进程并发写同一文件 | 各自差分互相覆盖，可能少算 |
| 先删后建同名文件 | 被识别为新建，旧数据丢失 |
| 稀疏文件 | 逻辑大小变化 ≠ 实际写入字节 |

**影响**：估算值只能作为"量级参考"，不能用于精确统计。
**建议**：这也是为什么 UI 上必须显示 `≈`，并且日志里会标注「估算」。

## 二、ETW 精确模式限制

### 2.1 启动前已打开的长期句柄 → 永久「未知路径」

`FileKey → 路径` 映射靠监听 `Create` 事件建立。程序**启动之前**就已经打开、并且一直不关闭的句柄（数据库连接、日志文件、正在下载的大文件），永远不会产生 `Create` 事件。

**影响**：这些文件的写入会永久显示为「未知路径」，无法做排除过滤，也无法在通知里显示路径。
**默认行为**：计入统计，**不弹窗**（避免噪音）。可在设置里打开「未知路径也提醒」。
**建议**：开机后尽早启动本工具，以提高映射命中率。设置 → 状态里的「路径映射命中率」反映这个比例。

> **明确不采用的做法**：启动时全盘枚举文件来建立初始映射。几十万文件需要数秒到数分钟，
> 且仍然无法关联到具体的 `FileKey`（`FileKey` 是内核对象标识，无法从路径反推）。

### 2.2 `FileKey` / `FileObject` 重用

映射表用两个键空间：`FileKey`（文件的持久标识）与 `FileObject`（每次打开的文件对象，本质是内核对象地址）。

两者都会在对象释放后被内核**复用**给新文件 —— 其中 `FileObject` 是**地址级**复用，回收速度比 `FileKey` 快得多。

**缓解**：`Cleanup(13)` / `Close(14)` 事件到达时**立即移除 `FileObject` 映射**（不移除 `FileKey`，因为同一文件可能还有别的句柄在用）；
`NameDelete(11)` / `DeletePath(26)` 移除 `FileKey` 映射。
**残留风险**：如果 `Close` 丢失（见 2.3），复用窗口内可能把旧路径错配给新文件。
**影响**：极小概率下提醒里的路径是错的。

### 2.3 `Close` 事件不保证到达

以下情况 `Close` 不会产生或不会被处理：进程被强杀、系统关机、驱动持有句柄、ETW 缓冲丢失。

**缓解**：TTL 5 分钟 + LRU 上限 20 万条，过期或超限自动清理。
**影响**：映射表可能短暂残留过期条目，占用少量内存；命中率统计会有轻微误差。

### 2.4 精确模式必须整体以管理员运行

ETW 的 `Microsoft-Windows-Kernel-File` 是内核 provider，**必须管理员权限**才能开启实时会话。

**影响**：UI 也会以管理员身份运行（见 5.2 为何不做双进程）。
**建议**：切换到精确模式时会触发**一次** UAC；之后用任务计划 `/RL HIGHEST` 自启则登录时静默启动。

### 2.5 ETW 会话残留 / 被占用

程序崩溃或被强杀后，ETW 实时会话可能残留在系统里，导致下次启动报 `ERROR_ALREADY_EXISTS`。

**缓解**：程序启动时会检测同名会话并尝试清理后重建。
**影响**：如果清理失败（例如另一个进程正在使用同名会话），精确模式启动会失败并在状态页报错。

### 2.6 manifest 随 Windows 版本变化

`Microsoft-Windows-Kernel-File` 的字段布局由系统 manifest 定义，**不同 Windows 版本/补丁级别可能不同**。

**缓解**：不硬编码字段偏移，改为运行时通过 TDH（`TdhGetEventInformation`）查询真实 schema 并缓存。
**残留风险**：如果某个版本连字段名都改了（例如没有 `Size`），解析会失败。
**排查手段**：托盘右键 →「导出 ETW 诊断信息」，会 dump 已发现的所有事件 schema。

### 2.7 ETW 自身也会丢事件

ETW 的实时缓冲区（本程序申请 128 KB × 4~16 个）在事件速率极高时会溢出，丢失事件且**不总是报告**。

**影响**：极端负载下精确模式也可能漏报。
**缓解**：加大缓冲数量；同时靠治理降级（见 6.2）避免程序自身成为瓶颈。

### 2.8 只关心「写」，不跟踪删除与重命名的大小语义

工具聚焦"写入"这一件事。文件的**删除**、**重命名**、**权限变更**不会产生"写入大小"意义上的提醒。

**影响**：`WriteKind` 里区分了 `Create` / `Modify`，但"某程序删了 50 GB 数据"这类场景不在覆盖范围内。
**建议**：本工具不是数据防泄漏（DLP）或防勒索软件，定位是"写入行为观察器"。

### 2.9 模式 A 的「仅提醒新建文件」依赖 `CreateNewFile` 事件

模式 A（任意写入即提醒）默认勾选「仅提醒新建文件」，用来压制噪音。它依赖 ETW 的
**`CreateNewFile(30)`** 事件（关键字 `CREATE_NEW_FILE = 0x1000`）来判断"这是不是一个新建的文件"。

**为什么不用 `Create(12)` 判断**：`Create` 对**每一次 open** 都会触发（打开已有文件也会），
无法区分"新建"与"打开"。只有 `CreateNewFile(30)` 是"文件此前不存在"的权威信号。

**残留风险**：如果某个 Windows 版本不发出 `CreateNewFile` 事件，该选项会退化成"不提醒"（**而且不会报错**）。
诊断报告里有一行专门盯它：

```
CreateNewFile(30)：1234   ← 为 0 说明模式 A 的"仅提醒新建文件"永远不触发
```

**建议**：如果希望"任何写入都提醒"（即需求原文的"任意新写入就提醒"），
在 **设置 → 提醒** 里**取消勾选「仅提醒新建文件」**。

### 2.10 `Create(12)` 事件没有 `FileKey` 字段

这是 Kernel-File manifest 的既有事实，不是缺陷：

| 事件 | `FileKey` | `FileObject` |
|---|---|---|
| `NameCreate(10)` | ✅ | ❌ |
| `Create(12)` | ❌ | ✅ |
| `Write(16)` | ✅ | ✅ |
| `Close(14)` | ✅ | ✅ |

因此映射表必须同时用两个键空间，查询时按顺序试。
**踩过的坑**：曾经用 `FileKey` 统一当键，导致 `Create` 建映射时键恒为 0、映射表**永远为空**，
精确模式下所有写入都变成"未知路径"被丢弃（40 万次写入、零提醒、零报错）。
详见 [`docs/04-测试用例.md` 缺陷 9](04-测试用例.md#缺陷-9create-事件里没有-filekey代码却拿它当映射表的键--精确模式40-万次写入零提醒)。

## 三、阈值语义限制

### 3.1 「单次写入」是重建出来的，不是原始语义

用户在直觉里认为"保存一个 100 MB 文件"就是"单次写入 100 MB"。但在系统内部，NTFS 会把这一次 `WriteFile` **拆成几十到上百个 IRP**，每个 IRP 可能只有几百 KB 到几 MB。

如果按"单个 IRP ≥ 10 MB"判定，这个文件**一次都不会触发**。

**本工具的解法**：`OffsetCoalescer` 把满足下列条件的碎片**归并为一次逻辑写入**：

```
相同 FileKey + 相同 IssuingThreadId
且 Offset_{n+1} == Offset_n + Size_n
且两次事件间隔 < 200 ms（默认，可配）
```

**限制**：这个重建规则是**启发式**的，不是内核的真实语义。极端情况下会与"用户心里的一次写入"不一致。

### 3.2 Offset 归并的退化情形

| 情形 | 结果 |
|---|---|
| 应用自己就把大写入切成多次独立 `WriteFile`（中间有 > 200 ms 间隔） | 归并链断开，按多次小写入处理 → 可能不触发 |
| 多线程并发写同一文件的不同区域 | 已按 `IssuingThreadId` 分组，但同一线程内乱序写仍会断链 |
| 内存映射文件（`MapViewOfFile`）写入 | 走的是 page fault 路径，产生的 ETW 事件形态不同，归并可能失效 |
| 写压缩/加密文件 | 实际落盘字节与 `Size` 不同 |

**缓解**：即使归并失效，还有"同一文件 1 秒固定窗口累计"作为兜底判据。

### 3.3 固定窗口，不是真滑动窗口

窗口实现是**固定（tumbling）窗口**：窗口内累计，到阈值触发后**整体重置**。

**与真滑动窗口的差异**：

- 真滑动窗口：任意 1 秒内的累计都算
- 固定窗口：只在当前窗口周期内累计

**影响**：紧贴窗口边界的两段写入（例如 0.9 s 处写 6 MB、1.1 s 处写 6 MB）不会被合并为 12 MB。

**为什么这样选**：固定窗口是 O(1)、零分配；真滑动窗口需要维护时间序列，在每秒数万事件下 CPU 和内存都吃不消。

### 3.4 三种阈值口径需要向用户解释清楚

程序提供三种口径（P1 单次 IRP / P2 同文件窗口 / P3 同进程突发），默认 **P2**。

**风险**：如果 UI 文案只写"超过 10 MB"，用户会理解成"一次 IRP 超过 10 MB"，然后认为工具漏报。
**应对**：提醒正文与设置页均明确写「同一文件在 1 秒内累计写入超过 10 MB 时提醒（按逻辑写入量，非单次 IRP）」。

### 3.5 聚合提醒里的「大小」是求和值

当同一进程在短时间内产生多条提醒时，会被合并成一条，此时显示的 `Size` 是**各条之和**。

**影响**：用户可能误以为"某个文件写了 40 MB"，实际是 3 个文件共 40 MB。
**应对**：聚合后的路径文案为「C:\x.bin 等 3 个文件」，并带 `AggregatedCount` 字段。

## 四、提醒通道限制

### 4.1 专注助手 / 勿扰模式会静默 Toast

Windows 的「专注助手」或「勿扰模式」开启时，Toast 会被系统收进通知中心**不弹出横幅**，甚至完全不显示。

**影响**：用户以为工具没提醒。
**缓解**：托盘气泡是兜底通道；程序也会把事件写入日志，可在日志窗口回看。
**建议**：首次运行后确认 Windows 设置 → 系统 → 通知里 CWriteWatcher 的权限为「开」。

### 4.2 未打包桌面应用的 Toast 依赖 AppUserModelID

`ToastNotificationManagerCompat`（`Microsoft.Toolkit.Uwp.Notifications`）能在**未打包**的桌面应用里发 Toast，但依赖系统注册正确的 AppUserModelID（通常需要开始菜单快捷方式或注册表注册）。

**影响**：在某些精简系统、绿色版环境（没有开始菜单快捷方式）下，真实 Toast 可能发不出来。
**缓解**：`UseRealToast=false` 的**精简版**改用 `NotifyIcon.ShowBalloonTip`，由 Win10/11 外壳渲染为系统 Toast，兼容性更好，体积也从 26 MB 降到 2.4 MB。

### 4.3 通知历史自身会产生写入（已排除，但可被误改）

程序发出的 Toast 会被 Windows 记录到通知历史目录（`%LOCALAPPDATA%\Microsoft\Windows\Notifications\*`）。如果不排除，会形成**二次循环**：本程序发通知 → 系统写通知历史 → 触发监控 → 再发通知。

**缓解**：内置排除表已包含该路径，默认开启。
**风险**：如果用户在排除表里手动取消勾选这条规则，会立刻出现通知风暴。

### 4.4 托盘气泡在某些系统上不显示

部分系统/主题配置下 `ShowBalloonTip` 可能不弹（例如"显示通知"关闭、任务栏图标被折叠）。

### 4.5 两条系统通道可能被一起静默，此时只剩「自绘置顶窗」和「托盘图标变红」

**这是最容易被误判为「程序坏了」的一种情况。**

程序产生一条提醒时会同时做四件事（设置 → 提醒 里可逐项开关）：

| 通道 | 默认 | 走 Windows 通知平台？ |
|---|---|---|
| **自绘置顶提示窗** | ✅ 开 | **否** |
| Windows Toast | ✅ 开 | 是 |
| 托盘气泡 | ✅ 开 | 是 |
| 声音提示 | ❌ 关 | **否** |
| 托盘图标变红 4 秒 | 固定 | **否** |

**关键事实：Win10/11 上 `NotifyIcon.ShowBalloonTip` 也是由外壳渲染成 Toast 的，
和 Toast 走的是同一条通知管道。** 所以只要下面任意一条成立，
**Toast 与托盘气泡会一起失效，而且 API 完全不报错**（`Show()` 正常返回）：

1. **系统通知总开关被关闭** —— `HKCU\Software\Microsoft\Windows\CurrentVersion\PushNotifications\ToastEnabled = 0`
   （对应「设置 → 系统 → 通知」最上面那个开关）。**本项目实际踩过这个坑。**
2. 「专注助手 / 勿扰模式」开启。
3. 本应用在通知设置里被单独关闭，或被设为「仅显示在通知中心」。
4. 前台有全屏程序（游戏 / 视频）。

**怎么确认**：设置 → 提醒 → **「发送测试提醒」**。
它走完全相同的代码路径，并在按钮下方直接显示各通道的实际结果
（`置顶窗 ✓ / Toast ✗ / 气泡 ✗ / 声音 ✗` 之类）以及降级原因。
设置 → 状态 和「导出 ETW 诊断信息」里也有各通道的发送计数与「通道错误」。

**计数有增长但屏幕上没出现** → 就是被系统静默，不是程序问题。

**缓解（按可靠性排序）**：
- **打开「自绘置顶提示窗」**（默认已开）—— 它是程序自己画的顶层窗口，
  不经过通知平台，**任何系统设置都挡不住**。这是本项功能的最终兜底。
- 打开**声音提示** —— `SystemSounds` 不经过通知管道。
- 检查 `ToastEnabled` 是否为 1，以及「专注助手」是否开启。
- 所有提醒都会写入日志（右键托盘 → 查看日志），不受任何通知设置影响。

## 五、权限与交互限制

### 5.1 UIPI：跨权限无法唤起窗口

如果已运行的实例是**管理员权限**，而用户以普通权限再次双击 exe，第二个实例**无法**唤起第一个实例的窗口，也无法把它的窗口置顶 —— 这是 Windows 的 UIPI（用户界面特权隔离）限制，**无法绕过**。

**影响**：用户会看到"提示已在运行，但找不到窗口"。
**应对**：提示文案里明确说明这一点，并引导用户到系统托盘查找图标。

### 5.2 不做「普通 UI + 提权后台」双进程方案

本次**明确不做**双进程架构（普通权限 UI + 管理员权限后台采集）。

**原因**：会引入一堆跨权限问题——`Global\` Mutex 的 ACL、命名管道的跨权限通信、托盘出现两个图标、配置文件读写冲突——复杂度和故障面都远超收益。

**代价**：精确模式下 UI 也是管理员权限；切换模式需要重启程序。

### 5.3 切换模式需要重启

标准模式 ↔ 精确模式切换时，采集器需要重建（一个是文件句柄集合，一个是 ETW 会话）。

**影响**：切换时有短暂的监控空档；从标准切到精确需要一次 UAC 提权并重启。

### 5.4 创建自启计划任务需要一次管理员授权

精确模式的自启用任务计划 `/RL HIGHEST` 实现（登录时静默启动、不弹 UAC）。但**创建这个任务本身**需要一次管理员授权。

**影响**：第一次开启精确模式自启时会弹一次 UAC，之后不再弹。

### 5.5 单实例按会话隔离，多用户会话各自独立

单实例锁用的是 `Local\` Mutex（限定当前登录会话），不是 `Global\`。

**影响**：

- 同一用户会话内**只能运行一个实例**（符合预期）。
- **多用户同时登录**（快速用户切换 / 远程桌面）时，每个会话可以各跑一个实例，各自监控各自的配置。
- 这也意味着**无法**用一个实例统一监控全机器所有用户的写入。

## 六、资源与性能限制

### 6.1 CPU 平均 < 2% 是**目标**，不是保证

Windows Update、索引服务、Defender 全盘扫描期间，ETW 事件量可达**每秒数万条**。即使做了有界队列 + 零分配过滤，也无法保证 CPU 均值一定 < 2%。

**因此本项目的验收口径是「目标 + 自动降级」**：

- 正常使用：CPU 均值 < 2%
- 事件风暴：允许短时峰值
- 持续 > 10%：自动降级（见 6.2）

**判定方法**：看"正常使用场景"下的均值，不要用全盘扫描时的峰值去卡这个指标。

### 6.2 降级期间会漏报

四级治理的降级行为本身就会牺牲覆盖率：

| 级别 | 行为 | 后果 |
|---|---|---|
| L0 正常 | 全功能 | — |
| L1 轻载 | 扩大聚合窗口 | 提醒更延迟、更聚合 |
| L2 重载 | **暂停模式 A**，只保留阈值触发 | 模式 A 用户在此期间**完全收不到提醒** |
| L3 风暴 | `DropOldest` 丢弃 | 丢弃的事件**不产生提醒**（但会被计数） |

**影响**：系统高负载时漏报是**设计内的行为**，不是 bug。
**缓解**：降级必须留痕 —— 状态页显示"已降级至 L2 · 已丢弃 N 条事件"及具体原因；**CPU < 2% 持续 30 秒后自动逐级恢复**。

> 自动恢复是必需的。没有它，一次 Windows Update 全盘扫描会让工具**永久停在 L2**，
> 之后所有普通写入都不再提醒，而用户完全察觉不到。

### 6.3 标准模式全盘监控可能超出 150 MB 内存预算

见 1.5。句柄 + 每目录缓冲区的内存开销随目录数线性增长。

**结论**：**标准模式 + 全盘**这个组合无法保证 < 150 MB。UI 上对该组合有明确警告。

### 6.4 首次启动/大范围枚举有延迟

标准模式启动时（以及修改监控范围后）需要递归枚举目录树来建立句柄集合。

**影响**：监控范围很大时，从启动到"真正开始监控"之间有几秒到几十秒的空档；期间发生的写入不会被捕获。

### 6.5 事件对象在极端情况下的分配压力

`FileWriteEvent` 是 `readonly struct`，正常情况下路径字符串会被驻留（interning）复用。但高基数路径（大量不同文件名）下字符串驻留表本身会增长。

**缓解**：路径映射与驻留表都有容量上限与 TTL。

---

### 6.6 「内存 < 150 MB」的口径说明

Windows 上「内存占用」至少有三个口径，数值差异很大。本机实测（标准模式 + 默认监控范围，进程稳定运行后）：

| 口径 | 实测 | 说明 |
|---|---|---|
| 提交大小 / 专用字节 | **118.6 MB** | 进程独占内存，含页面文件提交 |
| 工作集（Working Set） | **182.4 MB** | 含与 .NET 运行时共享的代码页 |
| 峰值工作集 | 182.4 MB | — |

**判定**：按**提交/专用字节 118.6 MB** 口径**达标**（< 150 MB）；按**工作集**口径 182.4 MB，**超标**。

工作集偏高的主因是：标准模式必须**按目录数**分配 `ReadDirectoryChangesW` 通知缓冲区，
默认总预算 `Scope.BufferBudgetMb = 64`（MB），且这些缓冲区是**钉住（pinned）**的，不能被换出。

内存更敏感时可以：

- 调小 `Scope.BufferBudgetMb`（例如 24）
- 缩小监控范围 —— 标准模式默认覆盖整个用户目录 + ProgramData，目录数可能上千
- 改用**精确模式**（单个 ETW 会话，不按目录分配缓冲区，内存与目录数无关）

## 七、其他边界

### 7.1 只监控 C 盘

`PathUtil.IsOnDriveC` 会过滤掉非 C 盘路径。

**影响**：D/E 盘、网络映射盘、可移动磁盘的写入**完全不在监控范围内**。
**原因**：需求明确是"监控 C 盘文件写入"；且监控全部磁盘会成倍放大资源占用。

### 7.2 仅支持 x64

目标是 Windows 10/11 x64。不提供 x86 / ARM64 构建。

### 7.3 系统时间回拨会影响判定

静默时段、窗口计时、节流都基于**单调时钟或系统时间**。用户手工改系统时间、或休眠唤醒后时间跳变，可能导致：

- 静默时段短暂判断错误
- 固定窗口的累计被意外重置或延长

**影响**：低频、自愈，不影响长期正确性。

### 7.4 日志会被裁剪

日志默认上限 **10 万条 / 200 MB**，超出按**最旧优先**裁剪。

**影响**：长期不导出的话，早期记录会被自动删除。
**建议**：需要长期留档就定期导出 CSV/JSON。

### 7.5 排除表配置错误会直接导致漏报

排除表是**精确匹配优先**的，配置错误（例如把 `C:\Users\` 整个排掉）会导致大量本应提醒的写入被静默丢弃。

**影响**：**用户自己配错是最大的漏报来源之一**，比工具本身的能力限制更常见。
**建议**：状态页会显示「排除路径」计数；如果该计数异常高，检查排除表。

### 7.6 排除规则维度有限

排除表支持：**目录前缀 / 精确路径 / 扩展名后缀 / 文件名通配 / 完整路径通配 / 进程名**。

**不支持**：按文件大小排除、按写入频率排除、按时间段排除、正则表达式。
**原因**：匹配走的是零分配快路径（顺序为 目录前缀 → 精确 → 扩展名 → 通配），正则会让单次匹配成本上升一到两个数量级。

### 7.7 不是安全产品

本工具**只观察、不阻断**。它无法阻止任何写入，也无法隔离、加密或恢复文件。

**明确定位**：写入行为的**观察器与提醒器**，不是防勒索软件、不是 DLP、不是沙箱。

### 7.8 自启任务指向用户可写目录时的提权风险（部署注意）

**这是本工具唯一一条真实的提权路径，需要用户侧配合规避。**

精确模式下「开机自启」会创建一个 `/RL HIGHEST` 的计划任务，指向
`Environment.ProcessPath`（即程序自身）。于是形成一条链条：

```
程序放在用户可写目录（例如 D:\Tools\ 或用户目录下）
  → 同用户的任意低权限进程可以替换掉 CWriteWatcher.exe
  → 下次登录时计划任务以**最高权限**静默启动被替换的 exe
  → 该进程拿到管理员权限，且全程没有 UAC 提示
```

**为什么代码层面修不了**：任务必须指向一个固定路径，而"这个路径是否可写"是部署决定的。
程序也没有代码签名可供启动前自校验。

**缓解（推荐第一条）**：
- **把程序放到 `%ProgramFiles%\CWriteWatcher\`** —— 普通用户对该目录只有读+执行权限，
  替换 exe 需要管理员，链条断开。
- 如果必须放在用户目录：**不要开启开机自启**，改为每次手动启动（会弹 UAC，用户能看到）。
- 另外注意：**首次创建该计划任务本身就需要一次管理员授权**（见 5.4），
  所以攻击者无法在用户不知情的情况下悄悄加上这条自启。

> 顺带说明：这条风险与"程序自身是否可信"无关 —— 它来自
> 「以最高权限运行 + 从可写路径加载可执行文件」这个通用组合，
> 任何需要管理员权限的托盘工具都有同样的注意事项。

## 八、明确不做的事

| 不做 | 原因 |
|---|---|
| 文件系统过滤驱动（Minifilter） | 需要驱动签名、WHQL 认证、内核调试环境；开发和分发成本远超收益。ETW 已能拿到等价的 IRP 级信息 |
| 阻断/拦截写入 | 见 7.7，定位是观察器 |
| 任何联网、遥测、上传 | 需求明确要求本地运行 |

| 启动时全盘枚举建立初始映射 | 见 2.1 |
| 监控 C 盘以外的磁盘 | 见 7.1 |
| 历史趋势分析 / 图表报表 | 超出本次范围；日志可导出后自行分析 |
| 多用户统一监控 | 见 5.5 |
