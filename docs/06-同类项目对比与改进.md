## 二、结论：我们缺什么

### 2.1 ★ 已修复：事件丢失对用户完全不可见（两种模式都是）

**这是本次调研最重要的发现，而且它是个真问题。**

| 模式 | 状态（修复前） |
|---|---|
| 标准模式 | `ReadDirectoryChangesW` 缓冲区溢出（`ERROR_NOTIFY_ENUM_DIR`）**有计数**，但该计数**从未在任何界面或诊断里显示** —— 只在一条测试的失败信息里用过 |
| 精确模式 | `EVENT_TRACE_PROPERTIES.EventsLost` 字段**定义了却从未被读取**，连计数都没有 |

也就是说：**两种模式下的静默丢事件，用户都不可能知道。**

这恰恰是本项目自己的文档反复强调的失败类型 ——
「Windows API 大量存在不抛异常、不返回错误、但什么也没干的行为」。

**旁证**：`wtrace`（697 星，同为 C# + ETW）的 README 专门有一节
`WARNING: … events were lost in the session.`，并解释原因、给出处置建议。
成熟工具会把这件事说出来，我们没有。

**修复内容**：

1. `CollectorStats.ResyncCount` → **`LostEvents`**，统一两种模式的语义
   （标准模式 = 溢出**次数**，精确模式 = 丢失**条数**），字段注释写清差别。
2. 精确模式新增**周期性 `ControlTrace(QUERY)`**（30 秒一次，`Stop()` 前再补一次），
   把 `EventsLost` + `RealTimeBuffersLost` 读出来。
   这两个计数器**只存在于 `EVENT_TRACE_PROPERTIES` 里**，QUERY 是唯一读取途径。
3. 统计链路从「挑 3 个字段的元组」改成**整块传 `CollectorStats`** ——
   以后采集器再加字段不用改签名。
4. 三处显示：
   - 设置 → 状态 → 运行统计：`丢失事件  123  ← 日志不完整：ETW 缓冲区不足，这些事件已无法补回`
   - 托盘提示：有丢失时附加 `· 丢 123`（不弹窗打扰，但必须看得见）
   - 诊断信息导出：附带语义说明

**新增测试（3 个，全部双向验证过）**：

| 用例 | 断言要点 | 改回去的后果 |
|---|---|---|
| `采集器报告的丢失事件必须出现在快照里` | 123 必须原样到达快照 | 报 `Expected: 123 / Actual: 0` |
| `EVENT_TRACE_PROPERTIES_必须是120字节且关键偏移正确`（扩充） | `EventsLost@88`、`RealTimeBuffersLost@100` | 对调字段顺序后报 `Expected: 88 / Actual: 92` |
| `运行统计必须完整显示且包含丢失事件` | 标签不被裁切 + 文本含该项 | 删掉那一行后报 `Sub-string not found` |

> **为什么偏移断言很重要**：偏移错了不会报错，只会**静默读到垃圾值**
> （表现为计数乱跳或永远为 0）—— 那比没有这个功能更糟。

### 2.2 未做：SSD 耐久度 / TBW 视角（价值最高，但改动最大）

`DiskActivityMonitor` 与 `ssd-write-monitor` 的核心卖点是**SSD 寿命**：

- 读 SMART 主机写入总量（NVMe 用 `IOCTL_STORAGE_QUERY_PROPERTY` + 协议特定日志页；
  SATA 走 `MSStorageDriver_*` / `SMART_RCV_DRIVE_DATA`）
- 结合厂商标称 **TBW**，算出「已用掉多少寿命」并做趋势外推
- `DiskActivityMonitor` 还有**物理磁盘写入总量**（性能计数器），
  与逻辑文件 I/O 并列显示 —— 两者通常不等，差额是文件系统元数据与日志

**我们完全没有这一层。** 用户能看到「chrome 写了 24 MB」，
但看不到「你的 SSD 已经消耗了 45% 的 TBW」。

**为什么这次没做**：它是一个**独立功能**（新数据源 + 新界面 + 需要按盘型号匹配 TBW 数据库），
不是「改进」而是「加半个产品」。而且它需要 `DeviceIoControl` 直读 SMART，
涉及新的 P/Invoke 面与硬件兼容性（USB 硬盘盒经常不转发 SMART）。
**建议单独立项**，详见 §四。

### 2.3 ★ 已实现：聚合与趋势视图

两个同类项目都有「今天 / 本周 / 本月共写入多少」。我们原来只有**逐条事件日志**，
回答不了这个问题 —— 而它恰恰是关心 SSD 寿命的人最想知道的。

**已实现**：

| 位置 | 内容 |
|---|---|
| 日志窗口底部 | `2026-10-13 合计 ≈ 12.4 GB（1,234 条） · 本页 100 条 · ...` |
| 「按天统计」按钮 | 趋势窗口：按**本地日期**汇总，带峰值对比条 |

**实现要点（都是踩过才知道的）**：

1. **`SUM(Size)` 是对的，不能再乘 `AggCount`** —— `Size` 存的是**累计值**
   （聚合行的 `Size` 已经是该组所有写入之和，见 `AlertAggregator`）。
2. **按本地日期分组**：`date(Ts/1000, 'unixepoch', 'localtime')`。
   用 UTC 分组会让东八区晚上 8 点后的写入被算到第二天。
3. **精度保守**：`MIN(SizeExact)` 只有全精确才为 1。混进一条估算值就标 `≈`。
4. **聚合与分页共用 `BuildWhere`**：两边各写一份筛选，一旦只改一处，
   就会出现「列表 3 条、合计却是 5 条的量」这种对不上的情况 ——
   而两个数字单看都合理，极难发现。
5. 用户从标准模式切到精确模式后，历史数据里**既有估算也有精确**，第 3 条会真实触发。

### 2.4 不做：内核 minifilter 驱动路线

`MinifilterMonitor` / `EaseFilterSDK` 走的是**文件系统过滤驱动**。
这是唯一能同时做到「免管理员 + 精确单次写入 + 覆盖所有进程」的路线。

**明确不做**，理由与 `docs/05` §5.2 一致：
驱动需要 WHQL 签名（EV 证书 + 每年成本）、蓝屏风险由我们承担、
且内核代码无法用本项目的测试体系覆盖。**收益不抵风险。**

### 2.5 不做：KrabsETW 依赖

`krabsetw` 是微软官方的 ETW 封装，能省掉我们那几百行手写 P/Invoke。

**不做**，理由：它带**原生 C++ 库**，会打破本项目「单语言、零原生依赖、
`dotnet publish` 一条命令出单文件」的现状，还会让 `EtwStructLayoutTests`
那套「逐字节核对结构体布局」的测试失去意义。
**我们的 P/Invoke 已经被测试钉死了，换库是纯负收益。**

## 三、我们做得比它们好的地方

调研也用来确认「哪些设计是对的」，避免被带偏：

| 维度 | 本项目 | 同类项目 |
|---|---|---|
| **免管理员可用** | ✅ 标准模式全程普通用户 | ❌ `DiskActivityMonitor` / `ssd-write-monitor` 都需要管理员 |
| **零外部依赖** | ✅ 单文件 exe，无需 .NET / Python / smartctl | ❌ Python 运行时 + `smartmontools` 外部程序 |
| **免安装** | ✅ 复制即用 | ❌ 多数需要 `pip install` / 安装步骤 |
| **测试规模** | ✅ 187 个（含结构体偏移、DPI 布局、分配量实测） | 多数项目没有测试目录 |
| **多实例 / 残留会话** | ✅ `SingleInstanceGuard` + 崩溃残留 ETW 会话自动清理 | 多数未处理 |

> 「多实例」和「残留 ETW 会话」这两条我在调研前专门去代码里核对过 ——
> **都已经实现了**（`SingleInstanceGuard.cs`、`StartSession` 里的
> `ERROR_ALREADY_EXISTS → ControlTrace(STOP) → 重试`）。
> 记在这里是为了避免以后重复「发现」同一个已解决的问题。

## 五、这次调研的方法论收获

1. **「同类项目有什么」和「我们缺什么」是两件事。** 星数高不等于更相关 ——
   `fibratus`（2552 星）是安全传感器，与我们的定位差得远；
   反而是 2 星的 `DiskActivityMonitor` 命中了我们最大的功能缺口。
   **按「目标用户是否相同」筛选，而不是按热度。**

2. **调研的最大产出往往是「发现一个自己没意识到的 bug」，而不是「抄一个功能」。**
   这次的价值 90% 在 §2.1 —— 一个一直存在、两种模式都有、却完全不可见的静默失败。

3. **先查代码再下结论。** 我一度以为「多实例保护」和「残留会话清理」是缺口，
   去代码里核对后发现**都已实现**。如果不查，就会写出一个看起来很专业、
   实际上是错的改进清单。
