## 二、技术难点说明：全盘监控 + "单次写入大小" 在用户态的可行性

这是整个项目的**核心约束**，必须先讲清楚，因为它直接决定架构。

### 2.1 为什么"单次写入字节数"在普通用户态几乎拿不到

Windows 用户态能拿到文件变更的公开接口只有两条路：

1. **`ReadDirectoryChangesW`** —— 通知粒度是"这个目录下某个名字发生了变化"，返回 `FILE_NOTIFY_INFORMATION`，字段只有：文件名、动作类型（`FILE_ACTION_ADDED` / `MODIFIED` / `RENAMED_*` / `REMOVED`）、以及可选的旧名。
   **没有任何长度字段、没有偏移量、没有发起进程。**

2. **USN Journal（`FSCTL_READ_USN_JOURNAL`）** —— 卷级变更日志，粒度同样是"某文件被改了"，返回 USN、文件名、`USN_REASON_*` 标志（`DATA_OVERWRITE` / `DATA_EXTEND` / `FILE_CREATE` 等）。
   **同样没有字节数，也没有进程。**

真正的"某进程在偏移 X 处写入了 Y 字节"这个信息，只存在于 **文件系统驱动栈的 IRP 层**（`IRP_MJ_WRITE` 的 `Parameters.Write.Length`）。用户态唯一的正规读取渠道是 **ETW 的 `Microsoft-Windows-Kernel-File` provider**，它把内核态的写事件（含 `Size`、`Offset`、`FileKey`、`IssuingThreadId`）以事件流的形式暴露出来。

### 2.2 三条路的权限现实

| 通道 | 能否拿到单次写入字节 | 能否拿到进程 | 能否全盘 | 权限要求 |
|---|---|---|---|---|
| `ReadDirectoryChangesW` | ❌ 只能靠大小差分**估算** | ❌ 只能靠句柄枚举**猜** | ⚠️ 需为每个目录开句柄 | **普通用户** |
| USN Journal | ❌ 无字节数 | ❌ 无进程 | ✅ 单句柄覆盖整卷 | **管理员**（打开 `\\.\C:` 卷句柄需提升） |
| ETW `Kernel-File` | ✅ 精确 `Size` | ✅ PID→进程名 | ✅ 全盘 | **管理员**（实时会话需提升） |
| Minifilter 驱动 | ✅ 精确 | ✅ 精确 | ✅ | 管理员 + **EV 代码签名** |

**结论（很重要）**：

> 想要"精确的单次写入字节数"，用户态**没有**免管理员的方案。
> 想免管理员，就只能接受"文件大小增量估算"这种近似值。

因此本项目必须做**双模式**，而不是在两者中硬选一个：

- **标准模式（默认，免管理员）**：`ReadDirectoryChangesW` + 大小差分估算。用户双击即用，零 UAC。
- **精确模式（可选，需管理员）**：ETW `Kernel-File` 实时会话。安装/启动时请求一次提升，此后由任务计划以最高权限静默自启（不再弹 UAC）。

UI 上必须诚实：估算值显示为 `≈ 12.4 MB (估算)`，精确值显示为 `12.4 MB (精确)`。

### 2.3 估算算法会怎么失真（必须写进"已知限制"）

`ReadDirectoryChangesW` 路线的估算逻辑是：在 500ms 的滑动窗口内，对同一个文件取两次大小快照，差值即"本次写入量"。

会失真的场景：

| 场景 | 现象 | 原因 |
|---|---|---|
| 缓慢持续追加 | 把 20 秒 × 1MB 的写入误判成"单次 20MB" | 窗口内累积增量被当成单次 |
| 原地覆盖写 | 完全不触发阈值 | 文件大小没变，差分恒为 0 |
| 内存映射写入 (MMF) | 部分丢失 | 脏页回写时机由内存管理器决定，通知会滞后/合并 |
| 先截断再重写 | 出现负增量 | `SetEndOfFile` 后大小回退 |
| 杀软/同步盘二次写 | 误报 | 同一路径被第二个进程再写一遍 |
| 缓冲区溢出 | 丢事件 | `ReadDirectoryChangesW` 返回 `ERROR_NOTIFY_ENUM_DIR`，需重新枚举目录，期间事件丢失 |

**精确模式（ETW）下这些失真全部消失**——这也是建议把它作为"进阶开关"的原因。

## 三、技术方案对比

### 方案一：`ReadDirectoryChangesW` 全盘递归监视（纯用户态）

- **原理**：遍历 `C:\` 下所有目录，对每个目录 `CreateFile(FILE_LIST_DIRECTORY | FILE_FLAG_BACKUP_SEMANTICS | FILE_FLAG_OVERLAPPED)`，投递异步 `ReadDirectoryChangesW`，用 IOCP 或 `ThreadPool` 收事件。
- **权限**：普通用户。少数 ACL 受限目录（`System Volume Information`、其他用户 Profile、`$Recycle.Bin`）打不开，跳过即可。
- **优点**：零依赖、零签名、零驱动、即开即用；单目录粒度可控；CPU 在事件稀疏时接近 0。
- **缺点**：
  - **句柄爆炸**。一台正常使用的 Win11 机器 `C:\` 下有 10 万 ~ 40 万个目录。每目录一个句柄，远超进程默认 1 万句柄上限，且内核内存开销大（每句柄 ~1KB 以上），直接违背"内存 < 150MB"。
  - 必须降级为"浅层 + 按需展开"（只监控前 N 层，或只监控白名单目录），覆盖面打折。
  - 无字节数、无进程 → 只能估算。
  - 缓冲区溢出丢事件。
- **适用**：只监控"指定目录"的轻量场景。

### 方案二：ETW `Microsoft-Windows-Kernel-File` 实时会话（推荐主力）

- **原理**：`StartTrace` + `EnableTraceEx2` 订阅 `Microsoft-Windows-Kernel-File`（GUID `{EDD08927-9CC4-4E65-B970-C2560FB5C289}`）的 `Write` / `SetEndOfFile` / `Create` / `Rename` 等关键字，`ProcessTrace` 在独立线程消费。`Write` 事件自带 `FileKey`、`Offset`、`Size`、`IssuingThreadId`。
- **权限**：**必须管理员**（内核类 provider 的实时会话，非提升会返回 `ERROR_ACCESS_DENIED`）。加入 "Performance Log Users" 组可部分缓解，但不通用。
- **优点**：
  - **精确**的单次写入字节数、精确的进程 PID→进程名。
  - **全盘覆盖，且只需 1 个会话句柄**——没有句柄爆炸问题。
  - 内核侧可做关键字级过滤（`EnableTraceEx2` 的 `EVENT_FILTER_DESCRIPTOR`），减少进入用户态的事件量。
- **缺点**：
  - 需要管理员 → UAC 与自启方式复杂化。
  - 原始事件量大：全盘写入在 Windows Update / 索引 / 编译时可达每秒数万条，若用户态过滤写得糙，CPU 直接爆掉 2% 预算。
  - **路径过滤无法在内核侧完成**（`FileKey` 要查表映射成路径），所以排除逻辑只能在用户态尽早执行——必须做到"零分配丢弃"。
  - 与 EDR / 杀软共存时可能被关注或抢占。
- **适用**：需要精确大小 + 全盘覆盖的主场景。

### 方案三：Minifilter 文件系统过滤驱动

- **原理**：KMDF minifilter，注册 `IRP_MJ_WRITE` / `IRP_MJ_SET_INFORMATION` 的 post 回调，通过 `FltSendMessage` 反转调用推给用户态服务。
- **权限**：管理员安装 + **EV 证书 + Microsoft 签名**（Win10 x64 起强制驱动签名）。
- **优点**：性能最优、信息最全、可在内核侧做路径过滤。
- **缺点**：开发/签名/维护成本极高（证书年费 + 签名流程 + WHQL 可选）；蓝屏风险；与杀软冲突风险高；不适合"小工具"定位。
- **适用**：产品级商用软件。**本项目不推荐。**

### 方案四（辅助）：USN Journal 变更日志

- **原理**：`\\.\C:` 卷句柄 + `FSCTL_READ_USN_JOURNAL` 增量拉取。
- **特点**：单句柄覆盖整卷，开销极低（Everything 就是这么做的）；但**无字节数、无进程**，需管理员。
- **定位**：不单独作为主方案，但非常适合做**兜底对账**——当 `ReadDirectoryChangesW` 缓冲区溢出时，用 USN 把漏掉的变更补回来。

### 对比总表

| 维度 | 方案一 RDCW | 方案二 ETW | 方案三 Minifilter |
|---|---|---|---|
| 单次写入字节 | 估算 | **精确** | 精确 |
| 进程归属 | 猜 | **精确** | 精确 |
| 全盘覆盖 | 句柄爆炸 | **单句柄** | 单驱动 |
| 权限 | **普通用户** | 管理员 | 管理员 + 签名 |
| CPU 均值 <2% | ✅（事件少） | ⚠️ 需精心过滤 | ✅ |
| 内存 <150MB | ❌ 全盘时超标 | ✅ | ✅ |
| 实现成本 | **低** | 中 | 极高 |
| 崩溃风险 | 无 | 无 | 有 |
| 适合小工具 | ✅ | ✅ | ❌ |

## 四、推荐方案

### 4.1 总体：双模式采集引擎 + 统一事件管道

采用 **方案二（ETW）为主、方案一（RDCW）为降级**，方案四（USN）作为可选对账。

```
┌─ 采集层 ────────────────────────────────────────────────┐
│  标准模式: ReadDirectoryChangesW (+ 大小差分估算)         │
│  精确模式: ETW Kernel-File 实时会话                       │
│            ↓ 归一化                                          │
│  FileWriteEvent { Time, Path, Size, SizeIsExact, Pid,     │
│                   ProcessName, Source }                    │
└──────────────────────────┬──────────────────────────────┘
                           ↓ 有界 Channel (DropOldest)
┌─ 处理层（单消费者线程）──────────────────────────────────┐
│  1. 排除表过滤（路径前缀 Trie，零分配）                    │
│  2. 进程排除表过滤                                         │
│  3. 阈值判定（模式 A / B / C）                             │
│  4. 节流（文件级 / 进程级 / 全局令牌桶）                   │
│  5. 静默时段判定                                           │
└──────────────────────────┬──────────────────────────────┘
                           ↓
        ┌──────────────────┼──────────────────┐
        ↓                  ↓                  ↓
   通知层              日志层              托盘层
   Toast + 气泡       SQLite 异步写        图标状态/暂停
   + 可选声音
```

### 4.2 为什么是这个方案

1. **满足核心诉求**：只有 ETW 能给"单次写入 10MB/50MB"一个**站得住脚**的判定。用户明确要求"单次写入超过 10MB / 50MB"，用估算值去判断这个阈值，误报率会高到用户想关掉它。
2. **不牺牲易用性**：免管理员的降级模式让用户双击就能跑，先看到效果，再决定是否提升权限换取精确度。
3. **资源可控**：ETW 单会话 + 有界 Channel + 零分配过滤，是唯一能同时满足"全盘 + CPU<2% + 内存<150MB"的组合。
4. **不碰驱动**：Minifilter 的签名与蓝屏成本，与"本地小工具"的定位完全不成比例。

### 4.3 技术选型明细

| 项目 | 选型 | 理由 |
|---|---|---|
| 运行时 | .NET 8 (`net8.0-windows`) | LTS，`Span`/`ArrayPool`/`Channel` 齐全 |
| UI | **WinForms** 托盘 + 设置窗体 | `NotifyIcon` 原生省事；比 WPF 内存更低，更容易压进 150MB |
| 通知 | `CommunityToolkit.WinUI.Notifications` (`ToastNotificationManagerCompat`) | 非打包应用可直接用 Toast，自动处理 AUMID 与快捷方式注册 |
| 托盘气泡 | `NotifyIcon.ShowBalloonTip` | Win10+ 会被系统转为 Toast，作为兜底 |
| ETW 消费 | 原生 P/Invoke `StartTrace/EnableTraceEx2/OpenTrace/ProcessTrace` | `TraceEvent` 库 GC 压力偏大；手写解析器更省内存 |
| 日志 | `Microsoft.Data.Sqlite` | 单文件、支持索引查询、体积可控；比 JSONL 全量加载省内存 |
| 配置 | `System.Text.Json` + 原子替换 | 无外部依赖 |
| 自启 | 标准模式：`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`<br>精确模式：任务计划程序（`/RL HIGHEST`） | 见下 |
| 单实例 | 全局 `Mutex` + 具名管道唤起 | 防止重复监控 |

### 4.4 自启方案的关键决策

- **标准模式**：写 `HKCU\...\Run` 一个值即可，开关即时生效，无需管理员，卸载时删值。
- **精确模式**：ETW 需要管理员，若用 `Run` 键启动则**每次开机都会弹 UAC**，体验灾难。因此精确模式下自启改为**创建任务计划**：
  - `schtasks /Create /TN "CWriteWatcher" /TR "<exe>" /SC ONLOGON /RL HIGHEST /F`
  - 任务计划以最高权限运行，**登录时静默启动，不弹 UAC**。
  - 创建该任务本身需要一次管理员授权（在用户打开"精确模式"开关时触发）。
  - 关闭自启时 `schtasks /Delete /TN "CWriteWatcher" /F`。

**三层节流兜底**

| 层级 | 默认值 | 作用 |
|---|---|---|
| 文件级 | 同路径 60s | 防止同一文件反复刷屏 |
| 进程级 | 同进程 30s | 防止某进程批量写触发风暴 |
| 全局令牌桶 | 1 条 / 2s，突发 5 | 最后的保险丝 |

**可选聚合模式**（建议默认开）：同一进程在 5 秒窗口内的多个事件合并为一条 —— "chrome.exe 写入 12 个文件，共 ≈ 340 MB"。

## 五、风险与限制

### 5.1 功能限制（不可绕过，需在 UI 说明）

| # | 限制 | 影响 |
|---|---|---|
| L1 | 免管理员模式下"单次写入大小"是**估算值** | 模式 B/C 的阈值判定存在误报/漏报 |
| L2 | 免管理员模式**拿不到可靠的进程名** | 提醒中的"进程名"可能为空或不准 |
| L3 | 原地覆盖写不改变文件大小 | 模式 B/C 在估算模式下**完全漏报** |
| L4 | 内存映射写入（SQLite/浏览器/大型软件）通知滞后合并 | 大小与时间均可能失真 |
| L5 | `ReadDirectoryChangesW` 缓冲区溢出会丢事件 | 需 USN 对账补齐（仅精确模式可用） |
| L6 | 精确模式需管理员 | UAC 提示；部分企业策略禁止 |
| L7 | Toast 在"专注助手 / 勿扰模式"下被系统静默 | 用户可能收不到提醒，需引导检查系统通知设置 |
| L8 | `System Volume Information`、其他用户 Profile 等无权限目录 | 该区域写入监控不到（影响极小） |
| L9 | 全盘监控无法覆盖到未挂载的卷 / 其他盘符 | 本工具只针对 C 盘（按需求） |

### 5.2 资源与稳定性风险

| # | 风险 | 缓解 |
|---|---|---|
| R1 | Windows Update / 索引 / Defender 全盘扫描期间事件量飙升 | 进程排除表 + 令牌桶 + 有界 Channel（`DropOldest` 丢弃而不阻塞） |
| R2 | ETW 消费线程 GC 压力 | 手写 ETW 解析，事件结构体走 `stackalloc`/`ArrayPool`，路径用 `Span<char>` 比较 |
| R3 | SQLite 写放大 | 批量事务（如每 500ms 或 200 条提交一次）；日志设环形上限（默认保留 10 万条 / 200MB） |
| R4 | 内存超 150MB | 排除表用 Trie 而非正则；日志不全量加载，表格分页查询 |
| R5 | 自启残留 | 卸载/退出时清理 `Run` 值与计划任务；提供"重置配置"入口 |
| R6 | 被 EDR 误判为可疑（订阅内核 ETW 会话） | 代码签名 + 开源/说明文档；提供"仅标准模式"选项 |
| R7 | 文件句柄泄露 | 所有句柄 `SafeHandle` 包装，进程退出时 `ProcessTrace` 正常停止 |

### 5.3 分发风险

- self-contained 单文件约 70–90MB（含 .NET 运行时）；framework-dependent 仅约 2MB 但需用户安装 .NET 8 Desktop Runtime。**建议默认 framework-dependent + 提供 self-contained 备选**。
- 未签名的 exe 首次运行会触发 SmartScreen 警告。若长期使用，建议代码签名。
